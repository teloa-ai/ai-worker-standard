## 1. 一つの契約で Worker、Team、Organization をつなぐ

従業員は作業の入口を提供します。チームは独自の作業の入口を提供し、メンバーがどう分担するかを示します。組織はさらにチームを組み合わせます。三者とも入力、出力、依存関係、責任、検収を明確にします。組織がメンバーの全作業を自動公開することはなく、組織への参加が個人の記憶の自動共有を意味することもありません。

作業プロファイルは必須拡張として記載します。`id = urn:teloa:profile:ai-work`、`version = "1.0"`、`required = true` です。これは本仕様の固定識別子であり、本人認証やオンラインサービスの入口ではありません。どのホストでも実装でき、Teloa アカウントは不要です。重要な意味を回避するために optional へ変更してはなりません。コアの agent フィールドだけを持つファイルが宣言できるのはコア交換への対応だけであり、完全な AI Worker 定義への適合を宣言してはなりません。

コア仕様の、空でない文字列、LocalId、固定参照、副作用のないインポート、未知の拡張に関するルールが引き続き適用されます。以下の構造は列挙したフィールドのみを許可し、任意と記したもの以外はすべて必須です。該当する内容がない場合は明示的な空配列を使い、null で代用してはなりません。各 id は所属配列内でのみ一意であり、参照位置は本附属書の規定に従って解釈します。

## 2. 拡張 data の構造

| フィールド | 型 | 用途と既定値 |
| --- | --- | --- |
| responsibility | Responsibility | 役割または構成体の判断ルール |
| resources | Resource[] | 方法、資料、アプリケーション、ポリシーのカタログ。空でもよく、掲載だけで全体として有効化が必須になるわけではない |
| works | 空でない Work[] | 外部に提供を約束する作業の入口 |
| requires | LocalId[]、任意 | すべての作業で共通に必要な resources。省略は空とみなす |
| routines | Routine[]、任意 | 定例作業の設定。省略は空とみなし、自動有効化しない |
| authorityRoles | AuthorityRole[]、任意 | 外部の承認、検収、責任の役割。省略は空とみなす |
| memoryPolicyRef | LocalId、任意 | purpose=policy のリソースを指す。存在する場合は全体依存関係に含め、省略はタスクをまたぐ記憶能力を宣言しないことを意味する |
| collaboration | Collaboration | organization では必須、agent では使用禁止 |
| governance | Governance、任意 | organization のみ使用可能。本版の AI org 定義への対応を宣言する場合は必須 |

**Responsibility** は五つの必須文字列配列 `triggers、autonomousActions、confirmationPoints、escalationRules、deliveryChecks` を含みます。それぞれ着手条件、自律的な動作、確認点、エスカレーションルール、納品時の確認を示します。triggers、autonomousActions、deliveryChecks は空であってはなりません。残り二つは、追加の業務確認やエスカレーションルールが実際にない場合に空にできます。確認配列が空でもホストの権限確認は免除されず、エスカレーション配列が空でも入力や権限が不足したまま実行を続けてはなりません。記述はツール権限を付与しません。コア instructions が継続的な責務を示し、Work とリソースが作業詳細を提供します。文章に実質的な意味があるかは内容レビューが必要であり、文字列が空でないだけでは判断できません。

**Resource** は `id:LocalId、title:空でない文字列、purpose、binding` と、任意の `requires:LocalId[]` を含みます。purpose は `method | knowledge | procedure | application | runtime | policy | trigger | template-reference` です。これらはリソースの用途ラベルであり、製品で新設が必須のリソース種別ではありません。binding は `kind、config` を含み、コア Capability の四種類のバインディングと config のルールを再利用します。プロトコルを重複定義しません。

Resource.requires は同一定義の resources だけを参照し、省略は空とみなします。固定資料には digest を付けることを優先し、可変の出典は実行時に読み取ったバージョンを固定しなければなりません。方法は完全なスキルパッケージを参照でき、SOP は方法または手順リソースを参照できます。読み取り専用のアプリケーション説明、モデル設定、ポリシーファイルを根拠に、アプリケーション接続済み、実行環境充足、ポリシー実施済みと表示してはなりません。

runtime、policy、trigger、またはリソースとして記述された application について、適合報告にはネイティブ形式、正確なバージョン、明確な処理担当を記録しなければなりません。担当はその形式を扱うホスト機能でも、明示的に割り当てられた人の工程でもかまいません。文章による説明しかなく実行を担う者がいなければ、必須条件を満たしません。この規約は既存のネイティブ形式を維持し、汎用の権限言語やスケジュール言語を新設しません。

**AuthorityRole** は `id:LocalId、name:空でない文字列、kind:human | service` を含みます。これは責務のスロットであり、アカウントではありません。ホストは信頼できる主体をバインドしなければなりません。service はホストが確認した外部サービス主体を指し、モデル自身が承認者になれることを意味しません。人の承認が必要な場合は human を宣言しなければなりません。役割の働きは、その役割を参照する検収、エスカレーション、ガバナンスの契約で決まります。

## 3. 各作業の入出力と納品

| Work フィールド | 型 | 意味 |
| --- | --- | --- |
| id、title、instructions | LocalId、空でない文字列、空でない文字列 | 作業の入口、名前、目標／方法の要件 |
| inputs、outputs | JSON Schema オブジェクト | 完全な入力オブジェクトと完全な出力オブジェクトをそれぞれ記述 |
| requires | LocalId[] | この作業に必要な resources。空でもよい |
| responsible | ParticipantRef | 主たる責任を担う一つの位置 |
| acceptance | Acceptance | 完了確認と検収責任 |

`ParticipantRef` は `self`、`member/<LocalId>`、`authority/<LocalId>` のいずれかです。self は現在の定義に対応するインスタンスを指します。member は現在の organization の直接の Member スロットだけを指し、タスク単位で参加する consultant も含みます。authority は現在の data.authorityRoles を指します。agent は member 参照を使ってはなりません。すべての参照は存在しなければならず、名前で推測してはなりません。responsible は self または member に限ります。外部の人は検収やエスカレーションを担当できますが、AI 実行者として扱ってはなりません。organization の self は構成体が外部への納品に責任を持つことを表します。その場合もホストは実際の実行者、入力配布担当、出力集約担当を記録し、組織の名義で実際の貢献者を置き換えてはなりません。

**Acceptance** は `criteria:空でない文字列配列、reviewer:ParticipantRef、independent:boolean` を含みます。criteria は確認可能な完了要件、reviewer は検収責務の位置です。independent=true の場合、ホストは実際のレビュー主体と対象成果の実際の実行主体が異なることを証明しなければなりません。複合成果では実際の貢献者を確認し、主責任者やチームの名義だけを比較してはなりません。二つのスロット、二つのセッション、二つの名称は独立性の証拠になりません。独立した主体であっても判断品質を自動的に証明するわけではありません。検収記録は採用した成果バージョンを固定します。構造検証の合格、モデルの完了、業務への採用は別々に記録します。

inputs、outputs のルートは `type:object` であり、`$schema = https://json-schema.org/draft/2020-12/schema` を宣言しなければなりません。[JSON Schema 2020-12](https://json-schema.org/draft/2020-12) の標準語彙を再利用し、独自の型言語は作りません。Schema は説明や `$defs` を含められます。すべての参照（`$ref`、`$dynamicRef` を含む）は当該 Schema 文書内だけを指し、入れ子の `$id` で参照の文書境界を変更してはなりません。インポート時にネットワーク経由で参照を解決してはなりません。実装は未対応の語彙や制約を報告し、無視した後で検証合格としてはなりません。format を重要な検収に用いる場合、対応する形式検査能力を明示的に宣言して検証する必要があります。

入力が不足する場合は補完待ちと報告します。出力不足や型不一致があれば、その成果契約に適合すると宣言してはなりません。文字列の数値化、小数の切り捨て、false の 0 への変換を暗黙に行いません。Schema default は記述であり、利用者がその値を提供または承認したことを自動的に意味しません。自由文の成果は文字列フィールドに格納できますが、業務上の証拠と判断品質は引き続き acceptance で確認します。

**依存関係の確認：** まずコア capabilities とその R05/R06 条件を満たし、次に data.requires、memoryPolicyRef、選択した Work.requires の和集合を取り、Resource.requires を再帰的に展開します。参照欠落またはリソース依存の循環は定義エラーです。接続、権限、解釈機能の不足は対応する作業が未準備であることを意味します。他の作業専用のリソースが未設定でも、現在の作業は阻止しません。全体の必須依存関係の不足は、全体の実行を引き続き阻止します。解析への対応、設定の準備完了、実際の権限は別々に報告し、部分的な利用可能性を全体が実行可能であるとの宣言にしてはなりません。

## 4. 定例作業と経験

**Routine** は `id:LocalId、work:LocalId、policyRef:LocalId` と、任意の `triggerRef:LocalId` を含みます。work は現在の works、policyRef は purpose=policy のリソース、triggerRef は purpose=trigger のリソースを参照します。実行役割は現在の定義にバインドされたインスタンスに帰属します。作成者、スケジュール所有者、実際の認可主体はホストが別途バインドし、Worker と同一である必要はありません。インポート時に別の従業員を作成したり、定例作業の公開範囲を広げたり、他のメンバーへ移したりしてはなりません。

triggerRef の省略は未設定を意味します。存在してもトリガーの定義だけを表し、インスタンスでは既定で無効です。トリガー形式はホストが処理します。Teloa の既存の daily/weekly やローカルイベントは実際の対応範囲のみを宣言し、任意の cron や外部イベントを黙って近似してはなりません。実際の作業と実際のトリガーを検証した後、配備担当者が有効化します。

定例作業の policy は、入力ウィンドウ／カーソル、入力なし・無効入力時の動作、トリガーの重複排除と業務処理の記録、再試行、並行実行／補完実行、予算、通知、停止条件を明示しなければなりません。不足がある場合は設定を保持できますが、有効化してはなりません。起動成功は処理成功を意味しません。合意した成果状態に達した場合だけ業務処理状態を進め、再試行で新しいトリガー番号を使って業務上の重複排除を回避してはなりません。統一された固定の再試行回数や「二回進展がなければ停止」といった業界共通ルールはありません。

memoryPolicyRef が定義するのは経験の保存、出典、範囲、レビュー、撤回のルールだけであり、作成者の私的な記憶を含めません。template-reference リソースは出典付きのテンプレート素材です。過去のログを新インスタンスが直接経験した事実と扱ってはなりません。共有従業員の個人、業務、プロジェクト、グループのコンテキストは、引き続きホストの権限に従って分離します。同じ従業員インスタンスが複数チームへ参加しても、各チームの履歴が相互に読めるとは限りません。

## 5. チーム協業と組織ガバナンス

| Collaboration フィールド | 型 | 意味 |
| --- | --- | --- |
| roles | RoleAssignment[] | すべての直接 Member をそれぞれちょうど一回含める |
| coordinator | ParticipantRef、任意 | 指定する場合、現在の直接 Member スロットだけを指せる。省略時に自動選任しない |
| handoffs | Handoff[] | 明示的な責任と資料の引き継ぎ関係。空でもよい |
| sharing | Sharing[] | 共有リソースの想定受信位置。空でもよい |
| stop | StopPolicy | 有限の協業、進展なし、エスカレーションのルール |

**RoleAssignment** は `member:LocalId、duty:空でない文字列、participation:member | consultant` を含みます。duty はこの構成内での分担を説明し、メンバー本来の責務を書き換えません。競合時は影響する作業を停止します。consultant はタスク単位で参加するコンサルタントであり、自動的にグループへ参加したりグループ履歴を得たりしません。両種のスロットの固定定義参照は、コアルールに従って解決します。参加範囲はインスタンスのバインディングとタスクの権限付与で実現します。

coordinator と Work.responsible は consultant スロットを指すこともできますが、明示的に依頼し、現在の作業への参加確認を得なければなりません。その場合もタスク単位の参加であり、チームの恒久的な管理や全グループ履歴の取得を意味しません。`member/` は Member スロットを参照する構文であり、participation の member 値とは別の概念です。

**Handoff** は `id:LocalId、from:WorkRef、to:WorkRef、when:空でない文字列、inputs:オブジェクト` を含みます。WorkRef は `member/<memberId>/<workId>` のみを許可し、現在の構成体の直接メンバーが宣言した作業を参照します。メンバー定義のバージョンは Member.ref から取得します。成果を生成済みのメンバー作業から受信側メンバー作業への引き継ぎを表します。`self/<workId>` は未対応であり、構成体の入口／出口を同じ参照意味に混在させません。サブチームは自身の works を外部に公開し、内部メンバーを直接貫通して参照しません。

Handoff.inputs のキーは受信作業の入力オブジェクトのトップレベルフィールド名、値は送信作業の出力オブジェクトのトップレベルフィールド名です。どちらも元の文字列として解釈し、式、スクリプト、ドット区切りパスを実行しません。フィールドは対応する Schema.properties に宣言されていなければなりません。コピーした値は、受信側 Schema の実際の検証にも合格する必要があります。受信作業に必要な他の入力は明示的に補い、不足している場合は不足を返し、受信成功を装ってはなりません。when は業務条件であり、明示的な割当または対応済みトリガー機構による確認があって初めて引き継ぎに進みます。文章があるだけで監視が実装済みとは宣言できません。

構成体 Work の入力配布と出力集約は、ホストのネイティブなオーケストレーション、または明示的に割り当てたコーディネーターが行います。本版では入口／出口のマッピング言語を新設しません。適合報告には、どの構成体入力がどのメンバー作業に入るか、各必須出力を誰のどの固定成果から得るか、誰が完全性を確認するかを明記しなければなりません。定義の静的検証はこれらのマッピングの実行を証明しません。マッピングや担当が未確定の場合、対応する構成体の作業を準備完了としてはなりません。構成結果は自身の outputs Schema と acceptance を満たす必要があり、メンバーの任意出力を自動的につなげてチーム成果としてはなりません。

実際の引き継ぎごとに、出典作業／Run、成果バージョン、送信・受信主体、マッピング後の資料、許可範囲、受信／拒否結果を固定します。受信側が確認し、作業の帰属を確立して初めて引き継ぎ完了とします。契約に必要で、かつ権限を得た資料だけを渡します。会話全体、私的記憶、接続資格情報を暗黙に引き継いではなりません。グループへのメッセージ送信と引き継ぎ成功は別々に記録します。

**Sharing** は `resource:LocalId、recipients:空でない ParticipantRef 配列` を含みます。resource は現在の resources を参照し、受信者は現在の member に限ります。可視性と具体的なバージョンは引き続きホストの認可で決まります。sharing は権限付与ではなく、共有リソースをすべてのメンバーの必須依存関係へ自動変換するものでもありません。作業で必要な場合は、受信作業の入力または依存関係で明示的に受け止める必要があります。

**StopPolicy** は `maxHops:正の整数、maxNoProgress:正の整数、escalateTo:ParticipantRef` を含みます。カウントは同じ作業とそこから派生する引き継ぎ連鎖に適用し、従業員の交代や再試行でリセットしません。maxHops は引き継ぎ回数を制限します。maxNoProgress は、新しい検証可能な証拠の追加または宣言済み検収項目の改善がない連続ラウンド数を制限します。いずれかの上限に達した場合、追加の割当を停止してエスカレーションします。再開には信頼できる主体による明示的な対処と新しい記録が必要です。値はシナリオに応じて設定し、従業員の能力スコアではありません。

**Governance** は `accountable:ParticipantRef、changePolicyRef:LocalId` を含みます。accountable は組織範囲の責任位置です。changePolicyRef は purpose=policy のリソースを指し、全体依存関係に自動的に含めます。このポリシーは、メンバーの任命／解任、定義と制約の変更、停止、進行中の作業の扱いを明示しなければなりません。組織レベルのデータ、予算、実行制限は data.requires 内の policy/runtime リソースで表します。継承すべき制約は適用メンバーと範囲を明示し、ホストが検証しなければなりません。制約によってメンバー権限を自動拡大してはなりません。競合時に緩い方を選んで許可してはなりません。

AI Team は協業契約を使用し、本版の AI Organization 定義はさらに governance を備えなければなりません。両者は同じ organization コア型を使い、人数で区別しません。新たな組織権限、実際のメンバー管理、組織間のアイデンティティシステムは、この定義仕様だけで自動成立するものではありません。

完全な Team または Organization 定義への適合を宣言する場合、メンバー参照閉包内の agent はすべて AI Worker 定義契約を満たし、organization はすべて本附属書の協業契約を提供しなければなりません。すべてのサブチームに governance を要求するわけではありません。コアフィールドだけの一時的 Agent は、Worker の実行機構が権限に従って呼び出せますが、本版に適合した持続的メンバーとして扱ってはなりません。外部の人またはサービスの検収位置は authorityRoles で表します。

## 6. ホストのバインディングと実際の実行

バインディング記録は配備環境に保存します。すべてのホストに同じデータベースや JSON 構造を強制しませんが、以下の情報を確認できなければなりません。

| 記録項目 | 必ず区別する内容 |
| --- | --- |
| 定義位置 | ルート定義の id/revision、各階層の Member.id からなるスロットパス、その終点の固定定義 |
| インスタンス選択 | 新規作成か再利用かの明示、実際のインスタンスのアイデンティティとバージョン、所属する信頼主体。インポート段階では作成しない |
| 継続するアイデンティティ | タスクをまたいでインスタンスを追跡可能にする。モデル、セッション、一時的 Agent、Run のアイデンティティは個別記録。有効化、停止、退役、再開権限を確認可能にする |
| タスクと認可主体 | 管理主体、タスク起案者、定例作業所有者、リソース認可主体を個別記録。共有 Worker は一人の全権限の共有を意味しない |
| 再利用関係 | 複数スロットが同一インスタンスにバインドされるか。本版での共有は同じ固定定義に対応する必要があり、同名だけで推測しない |
| 責任役割 | authorityRoles に対応する信頼主体と human/service 型。承認者はモデルの自己申告から決めない |
| 実行条件 | 選択した作業、リソースとネイティブ形式／バージョン、実際の接続、有効な権限、モデル、リソース制限 |
| バージョンと変更 | バインディングのバージョン、採用したメンバー分担、制約と資料のバージョン、変更後の未完了作業の扱い |

同じテンプレートから二つのインスタンスを作成する場合と、同じインスタンスが複数チームを兼任する場合は、別の関係として記録しなければなりません。共有インスタンスのグループ可視性と実行権限は所属作業ごとに確認し、予算は実際に適用される同一枠として記帳します。重複バインディングで本来一枠しかない予算を二枠取得してはなりません。

一回の実行は、ルート定義、選択作業、実際の実行主体、資料・リソースのバージョン、有効な権限、成果バージョンまで追跡できなければなりません。メンバーの交代やテンプレート更新が旧 Run を密かに引き継いではなりません。元の実行の再開、終了、新規タスク作成は明示的な変更ポリシーに従います。ホストが重要な制約を満たせない場合は定義を保持して阻害要因を報告し、注記へ格下げして実行を続けてはなりません。

作業入力、検索資料、過去のメッセージ、ツール出力は出典付きの作業資料であり、Worker 定義の変更や権限拡大を認める信頼済み指示ではありません。ホストはこれらの資料と権限の出所を区別しなければなりません。Worker は一時的 Agent を呼び出せますが、外部への納品は選択した Worker に帰属します。一時的実行者が自動的に Team メンバーになることはありません。独立レビューでは実際の貢献者と代理関係を確認し、新しいセッションや一時的な補助者によって自分の成果に独立したアイデンティティを作り出してはなりません。

実行記録は、少なくとも作業成功、失敗、部分完了、結果不明、停止を区別します。ホストは独自の状態名を使用できます。部分出力やタイムアウト後の応答を自動的に作業成功としてはなりません。外部副作用があり結果が不明の場合、再試行を決める前に元の操作状態を確認しなければなりません。タスク要件、検収条件、結果、制限が品質評価の範囲を構成します。全業界共通の点数や「一度合格すれば配属可能」というルールは規定しません。

## 7. OASF と Agent Spec を採り入れる範囲

OASF discovery は独立した拡張として保持します。固定バージョンのネイティブ discovery Schema URI を id に、同じ schema_version を version に使い、ネイティブ payload をそのまま data に格納します。発見情報だけなら required=false とし、無視できない実行選択条件に用いる場合は required=true を宣言して意味を検証しなければなりません。分類自体は権限を付与しません。この wrapper は本仕様のマッピング方法であり、ネイティブの A2A リクエスト本文ではありません。

たとえばネイティブ payload の `schema_version、skills、domains` は元の名前と意味を維持します。skills は能力カテゴリ、domains は分野です。固定カタログに実在する項目だけを OASF 分類検証合格と宣言できます。ホストは信頼できる固定 Schema／分類スナップショットをオフラインで利用でき、URI のインポートだけでサービスに自動アクセスしません。対応する分類がない場合は未マッピングであることを保持し、公式番号を捏造してはなりません。[OASF discovery](https://docs.agntcy.org/oasf/discovery-extension/)

OASF の record メタデータと locators はエクスポート用ビューにできます。出典、バージョン、未対応フィールドは適合報告へ記載します。これらは本仕様の固定リビジョンや実際のインスタンス識別子の代わりにはなりません。元定義を単一の正本として保持し、派生ビューを独立して変更可能な第二の実行設定にしてはなりません。[Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Agent Spec の参照、入出力、構成の考え方を本版の Work と Handoff に採用します。`$component_ref` は設定内参照であり、エクスポート時には本仕様の固定定義／リソースとの対応を明示的に構築する必要があります。その入出力プロパティ一覧と本版のオブジェクト Schema は変換が必要で、フィールド名の変更だけでは足りません。インターフェース、制約、実行の意味を完全に保持した場合にだけ、選択したバージョン／サブセットのマッピング対応を宣言できます。[Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

Swarm、ManagerWorkers は適合するチームのマッピング先にできます。会話の引き継ぎ、作業メンバーが利用者と直接対話できるか、メッセージの流れをそれぞれ確認しなければなりません。現在の契約は Teloa がその実行エンジンへ切り替えることを要求せず、全チームを管理者―作業者モデルへ強制変換しません。

## 8. 既存設計の対応範囲

| 既存要素 | 本仕様での対応先 |
| --- | --- |
| A01 役割のアイデンティティと使命 | コアの id/revision/name/instructions。アバターなどの表示情報は非重要拡張で保持 |
| A02 責任と判断 | responsibility の五つのフィールド群。実際の権限はホストでバインド |
| A03 Skills | purpose=method の resources。完全な方法パッケージまたはネイティブ方法リソースを参照 |
| A04 知識 | purpose=knowledge。出典、バージョンまたはダイジェストを保持し、作業単位で参照 |
| A05 SOP | purpose=procedure とそのリソース依存関係。役割間の引き継ぎは collaboration で表現 |
| A06 作業テンプレート | works の目標、I/O、依存関係、責任位置、検収 |
| A07 定例作業 | routines、ネイティブトリガー、実行ポリシー。未設定／無効の状態はホストが記録 |
| A08 アプリケーション接続 | purpose=application、ネイティブバインディング、実際の接続。カタログ上の宣言はインストール成功を意味しない |
| A09 権限 | 必須 policy リソース、作業範囲、ホストの信頼できる権限付与。資格情報はエクスポートしない |
| A10 実行と作業空間 | runtime リソース要件、およびホストのモデル、予算、ファイル範囲のバインディング |
| A11 経験 | memoryPolicyRef と出典参照。実際の私的経験はインスタンスに残す |
| A12 成果と品質 | outputs、acceptance、実行証拠。構造と業務品質を別々に確認 |
| T01 共通目標 | organization.instructions と外部向け works |
| T02 役割責任 | Member、collaboration.roles、Work.responsible、authorityRoles |
| T03 共有コンテキスト | sharing、作業入力、ホストによる範囲別の権限付与 |
| T04 協業上の引き継ぎ | handoffs、入力マッピング、受信確認、stop |
| T05 作業の予定 | メンバーまたは構成体の routines、procedure、調整分担 |
| T06 権限とリソース | 全体／作業の requires、メンバー本来の権限、ホストの実際の割当枠 |
| T07 チーム検収 | 構成体の outputs/acceptance、メンバーの貢献、固定成果バージョン |

現行コミュニティリポジトリの RoleDefinition、GroupDefinition、RoleWorkDelegation、RunRoleSnapshot、リソースパッケージの関係はマッピング対象とし、新しい製品オブジェクトへ変更しません。Teloa の「AI 従業員」は Worker の製品形態に対応します。RoleDefinition、固定役割バージョン、実際の Role インスタンスが共同でマッピングに関与し、単独の改名では適合を証明できません。role-coordination は静的な調整関係だけを表します。グループ作成、作業割当、自動引き継ぎには、それぞれ実際の対応と権限が必要です。

Teloa の `kind: employee | twin` は製品の役割種別です。どちらも同じ作業契約を満たせば Worker へマッピングできますが、twin が本人に代わって承認する権利を生むことはありません。元の kind は適合報告または非重要の製品表示拡張で保持し、コア kind に直接記述してはなりません。`scopes` と dataScope/executionScope は必須の範囲ポリシーとホストの認可バインディングへ対応付けます。ホスト間で業務範囲を対応させられない場合、関連する作業は未準備のままとします。これらは重要な制限であり、無視可能な表示拡張だけに保存してはなりません。ここでのフィールドはコミュニティリポジトリの `packages/contract/src/roles.ts` と照合していますが、変換器の実装済みを意味しません。

Grok の公開 recipe の profile は役割説明、skills は方法、routines は作業と未設定の定例作業、plugins は設定待ちのアプリケーション、memory は出典付きのテンプレート素材へ対応付けます。profile 型の作業指針と log 型の作成者ログは別々に保持します。gettingStarted は入口の案内のみとして扱います。責務、日程、検収情報が不足している場合は不足を報告し、名前や元作成者の経験から推測して作ってはなりません。完全な原本とそのダイジェストを適合報告から関連付け、重要な意味を無視可能な拡張に隠してはなりません。Grok Team Bot は共有 Worker に対応し、名称だけで複数 Worker の Team を自動生成してはなりません。

Grok Team Bot の公開文書では個人の定例作業は作成者に帰属し、接続も現在の利用者または Bot の資格情報で動作する場合があります。したがって、マッピング時は定例作業所有者、実行アイデンティティ、資料の可視範囲を保持しなければなりません。全員の定例作業を共有 Worker の全員向けタスクへ統合してはなりません。これは出典動作のマッピング要件であり、他のホストにその権限既定値の複製を要求するものではありません。[Team Bots](https://docs.x.ai/grok-bot/team-bots)

**私的な定例作業の保存先：** 個人の定例作業は、所有者と可視範囲で分離されたホスト側の設定だけに対応付け、Worker が宣言済みの Work を参照します。共有定義の routines に含めたり共有エクスポートしたりしてはなりません。適合報告には「私的なインスタンス設定として保持し、定義には含めていない」と記載し、報告自体もその可視範囲に従わなければなりません。元作成者が明示的にテンプレートとして公開し、私的内容を除去した後に限り、テンプレートを定義の routines に含められます。インポート後も既定では無効です。所有者、可視性、作業参照を保持できない場合はマッピング不能を報告し、統合したり黙って失ったりしてはなりません。

適合報告は少なくとも元形式／バージョン／ダイジェスト、対象定義リビジョン、フィールド対応、保持／変換／未対応項目、および未対応項目が影響する作業を列挙します。原本の保存は意味のマッピング成功と同じではありません。変換で権限、引き継ぎ、検収条件を満たせない場合は、影響する作業を阻止しなければなりません。

## 9. 正例・反例と完了の宣言

[完全な構成例](../examples/composition-fixture.json)は、固定されたローカル定義集合を使って二人の従業員、この二つの従業員定義を再利用する二つのチーム、一つの入れ子組織、およびホストのバインディングと作業準備完了の期待値を表します。集合の外側の構造と説明はテスト用フィクスチャ形式であり、新しい配布プロトコルでも、Teloa に直接インポートできるリソースパッケージでもありません。

| 確認項目 | 必ず得られるべき結論 |
| --- | --- |
| スキル、記憶、定例作業がすべてゼロの単純な役割 | 定義可能。ただし明確な作業、I/O、責任、検収は必須 |
| 名前、プロンプト、kind=agent だけ | コア交換には適合し得るが、これだけで完全な AI Worker 定義を宣言してはならない |
| triggers、自律動作、納品確認が空 | 本版の作業附属書には不適合。製品名で補うことはできない |
| 同じ Worker が二つのタスクを開始し、モデルを変更 | 同一 Worker インスタンスと二つの独立した Run を追跡できなければならない。二つのセッションだけではアイデンティティの継続を証明しない |
| 同じ従業員定義が二つのチームに出現 | 定義の再利用だけを示す。同一インスタンスかはスロットのバインディングが決める |
| 一方の作業に専用アプリケーションがなく、他方の入力は完全 | 前者は未準備。後者は全体条件と自身の依存関係を確認し、前者によって自動的に阻止されない |
| サブ組織のバージョン欠落、循環、未知の必須 Profile | 組み立てを停止し具体的な参照を報告。別バージョンへの置換や無視はしない |
| 誤った受信フィールド、必須入力不足、出力型不一致 | 引き継ぎ成功や成果適合と表示できない。値の自動補完や型変換はしない |
| 二つのレビュースロットが同じ実際の実行主体にバインド | independent=true を満たさない |
| コンサルタントが一つのレビューだけに参加 | 全グループ参加、全履歴読み取り、新従業員複製を自動的に行わない |
| 予定にトリガーがない、またはポリシーが不完全 | 未準備の設定として保持し、有効化しない |
| OASF 分類が未知、または Agent Spec のパターンが非等価 | 未対応／マッピング差異を報告し、全面互換を宣言しない |

本仕様が宣言するのは構造と動作の契約です。文書検査、例の検査、実際の接続／モデル実行、独立実装の相互運用、業界での採用は別々に報告します。検証範囲と実装報告の要件は[適合性の説明](../CONFORMANCE.md)を参照してください。
