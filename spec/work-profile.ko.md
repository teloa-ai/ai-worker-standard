## 1. 하나의 계약으로 Worker, Team, Organization 연결하기

직원은 작업 진입점을 제공합니다. 팀은 자체 작업 진입점을 제공하고 구성원이 어떻게 분담하는지 설명합니다. 조직은 다시 팀을 조합합니다. 세 형태 모두 입력, 출력, 의존성, 책임 및 검수를 명확히 합니다. 조직이 구성원의 모든 작업을 자동으로 노출하지 않으며, 조직에 가입했다고 개인 기억이 자동으로 공유되지도 않습니다.

작업 프로파일은 필수 확장으로 나타납니다. `id = urn:teloa:profile:ai-work`, `version = "1.0"`, `required = true`입니다. 이는 이 명세의 고정 식별자이지 인증 또는 온라인 서비스 진입점이 아닙니다. 모든 호스트가 구현할 수 있으며 Teloa 계정이 필요하지 않습니다. 핵심 의미를 우회하려고 optional로 바꾸어서는 안 됩니다. 코어 agent 필드만 있는 파일은 코어 교환 지원만 선언할 수 있으며 완전한 AI Worker 정의 적합성을 선언해서는 안 됩니다.

코어 명세의 비어 있지 않은 문자열, LocalId, 고정 참조, 부수 효과 없는 가져오기 및 알 수 없는 확장 규칙을 계속 적용합니다. 다음 구조는 나열된 필드만 허용하며 선택 사항이라고 표시한 경우를 제외하면 모두 필수입니다. 해당하는 내용이 없으면 명시적 빈 배열을 사용하고 null로 대체해서는 안 됩니다. 각 id는 소속 배열 안에서만 고유하며 참조 위치는 이 부록의 명시적 규칙으로 해석합니다.

## 2. 확장 data 구조

| 필드 | 타입 | 용도 및 기본값 |
| --- | --- | --- |
| responsibility | Responsibility | 역할 또는 구성체의 판단 규칙 |
| resources | Resource[] | 방법·자료·애플리케이션·정책 카탈로그. 빈 배열 허용. 나열했다고 전체에서 반드시 활성화해야 하는 것은 아님 |
| works | 비어 있지 않은 Work[] | 외부에 약속하는 작업 진입점 |
| requires | LocalId[], 선택 사항 | 모든 작업에 공통으로 필요한 resources. 생략하면 빈 배열로 간주 |
| routines | Routine[], 선택 사항 | 정기 작업 일정. 생략하면 빈 배열로 간주하며 자동 활성화하지 않음 |
| authorityRoles | AuthorityRole[], 선택 사항 | 외부 승인·검수·책임 역할. 생략하면 빈 배열로 간주 |
| memoryPolicyRef | LocalId, 선택 사항 | purpose=policy 자원 참조. 있으면 전체 의존성에 포함. 생략하면 작업 간 기억 능력을 선언하지 않음 |
| collaboration | Collaboration | organization은 필수, agent는 사용 금지 |
| governance | Governance, 선택 사항 | organization만 사용 가능. 이번 판의 AI org 정의 지원을 선언하려면 필수 |

**Responsibility**는 다섯 필수 문자열 배열 `triggers、autonomousActions、confirmationPoints、escalationRules、deliveryChecks`를 포함합니다. 각각 인수 조건, 자율 행동, 확인 지점, 에스컬레이션 규칙 및 납품 확인을 설명합니다. triggers, autonomousActions, deliveryChecks는 비어 있어서는 안 됩니다. 나머지 두 배열은 실제로 추가 업무 확인이나 에스컬레이션 규칙이 없을 때 비워 둘 수 있습니다. 빈 확인 배열도 호스트 권한 확인을 면제하지 않으며, 빈 에스컬레이션 배열도 입력이나 권한이 부족한 상태에서 실행을 계속하도록 허용하지 않습니다. 설명은 도구 권한을 부여하지 않습니다. 코어 instructions는 지속적인 책임을 설명하고, Work와 자원은 작업 세부 사항을 제공합니다. 내용이 실질적인 의미를 갖는지는 별도 내용 검토가 필요하며 문자열이 비어 있지 않다는 사실만으로 판단할 수 없습니다.

**Resource**는 `id:LocalId、title:비어 있지 않은 문자열、purpose、binding`과 선택적인 `requires:LocalId[]`를 포함합니다. purpose는 `method | knowledge | procedure | application | runtime | policy | trigger | template-reference`입니다. 이는 자원 용도 라벨이지 반드시 새로 만들어야 하는 제품 자원 유형이 아닙니다. binding은 `kind、config`를 포함하며 코어 Capability의 네 바인딩 유형과 config 규칙을 재사용합니다. 프로토콜을 다시 정의하지 않습니다.

Resource.requires는 같은 정의의 resources만 참조하며 생략하면 빈 배열로 간주합니다. 고정 자료에는 digest를 우선 포함하고, 가변 출처는 실제 실행 때 읽은 버전을 고정해야 합니다. 방법은 전체 스킬 패키지를 참조할 수 있으며 SOP는 방법이나 절차 자원을 참조할 수 있습니다. 읽기 전용 애플리케이션 설명·모델 설정·정책 파일만으로 앱 연결 완료·실행 환경 충족·정책 집행 완료라고 표시해서는 안 됩니다.

runtime, policy, trigger 또는 자원으로 기술한 application에 대해서는 적용 보고서에 네이티브 형식, 정확한 버전 및 명확한 처리 주체를 기록해야 합니다. 처리 주체는 그 형식을 지원하는 호스트 기능이나 명시적으로 배정된 사람의 절차일 수 있습니다. 글로 된 설명만 있고 실제 실행을 맡는 주체가 없으면 필수 조건을 만족하지 않습니다. 이 규약은 기존 네이티브 형식을 유지하며 범용 권한 또는 일정 언어를 새로 만들지 않습니다.

**AuthorityRole**은 `id:LocalId、name:비어 있지 않은 문자열、kind:human | service`를 포함합니다. 책임 슬롯이지 계정이 아닙니다. 호스트는 신뢰할 수 있는 주체를 바인딩해야 합니다. service는 호스트가 확인한 외부 서비스 주체를 뜻하며 모델이 스스로 승인자가 될 수 있다는 뜻이 아닙니다. 사람의 승인이 필요하면 human을 선언해야 합니다. 역할의 기능은 이를 참조하는 검수·에스컬레이션·거버넌스 계약이 결정합니다.

## 3. 각 작업의 입력과 출력 및 납품

| Work 필드 | 타입 | 의미 |
| --- | --- | --- |
| id、title、instructions | LocalId, 비어 있지 않은 문자열, 비어 있지 않은 문자열 | 작업 진입점·이름·목표／방법 요구 |
| inputs、outputs | JSON Schema 객체 | 완전한 입력 객체와 완전한 출력 객체를 각각 기술 |
| requires | LocalId[] | 이 작업이 필요로 하는 resources. 빈 배열 허용 |
| responsible | ParticipantRef | 하나의 주된 책임 위치 |
| acceptance | Acceptance | 완료 확인과 검수 책임 |

`ParticipantRef`는 `self`, `member/<LocalId>` 또는 `authority/<LocalId>`입니다. self는 현재 정의에 대응하는 인스턴스를 뜻합니다. member는 현재 organization의 직접 Member 슬롯만 참조하며 작업별 consultant도 포함합니다. authority는 현재 data.authorityRoles를 뜻합니다. agent는 member 참조를 사용해서는 안 됩니다. 모든 참조는 존재해야 하며 이름으로 추측해서는 안 됩니다. responsible은 self 또는 member여야 합니다. 외부 사람이 검수와 에스컬레이션을 담당할 수 있지만 AI 실행자인 것처럼 표현해서는 안 됩니다. organization에서 self를 사용하면 구성체가 외부 납품을 책임진다는 뜻입니다. 이때도 호스트는 실제 실행자·입력 분배 담당·출력 취합 담당을 기록해야 하며 조직 명의로 실제 기여자를 대신해서는 안 됩니다.

**Acceptance**는 `criteria:비어 있지 않은 문자열 배열、reviewer:ParticipantRef、independent:boolean`을 포함합니다. criteria는 확인 가능한 완료 요구이고 reviewer는 검수 책임 위치입니다. independent=true이면 호스트는 실제 검토 주체가 검토 대상 결과물의 실제 실행 주체와 다름을 증명해야 합니다. 복합 결과물은 실제 기여자를 확인해야 하며, 주 책임자나 팀 명의만 비교해서는 안 됩니다. 두 슬롯·두 세션·두 이름은 독립성 증거가 아닙니다. 독립적인 주체라고 판단 품질이 자동 증명되는 것도 아닙니다. 검수 기록은 채택한 결과물 버전을 고정하며, 구조 검증 통과·모델 완료·업무 채택을 각각 기록합니다.

inputs와 outputs의 루트는 `type:object`여야 하며 `$schema = https://json-schema.org/draft/2020-12/schema`를 선언해야 합니다. [JSON Schema 2020-12](https://json-schema.org/draft/2020-12)의 표준 어휘를 재사용하고 독자 타입 언어를 만들지 않습니다. Schema에는 설명과 `$defs`를 포함할 수 있습니다. 모든 참조(`$ref`, `$dynamicRef` 포함)는 해당 Schema 문서 안만 가리켜야 하며, 중첩 `$id`로 참조의 문서 경계를 바꾸어서는 안 됩니다. 가져올 때 네트워크에 접속하여 참조를 해석하지 않습니다. 구현은 지원하지 않는 어휘나 제약을 보고해야 하며 무시한 뒤 검증 통과라고 해서는 안 됩니다. format을 핵심 검수에 사용한다면 해당 형식 검사 능력을 명시적으로 선언하고 검증해야 합니다.

입력 항목이 부족하면 보완 필요 상태를 보고합니다. 출력이 부족하거나 타입이 맞지 않으면 결과물 계약에 적합하다고 선언해서는 안 됩니다. 문자열을 숫자로, false를 0으로 암묵적으로 변환하거나 소수를 잘라내지 않습니다. Schema default는 설명일 뿐 사용자가 그 값을 제공하거나 승인했다는 의미가 아닙니다. 자유 형식 텍스트 결과는 문자열 필드에 넣을 수 있으며, 업무 증거와 판단 품질은 여전히 acceptance로 확인합니다.

**의존성 검사:** 먼저 코어 capabilities와 R05/R06 조건을 만족한 뒤 data.requires, memoryPolicyRef, 선택한 Work.requires의 합집합을 구하고 Resource.requires를 재귀적으로 펼칩니다. 참조 누락이나 자원 의존성 순환은 정의 오류입니다. 연결·권한·해석기 부족은 해당 작업의 준비 미완료를 뜻합니다. 다른 작업 전용 자원이 미설정이라고 현재 작업을 차단하지는 않습니다. 전체 필수 의존성 부족은 여전히 전체 실행을 차단합니다. 파싱 지원·설정 준비 완료·실제 권한을 각각 보고하며 일부 사용 가능 상태를 전체 실행 가능이라고 선언해서는 안 됩니다.

## 4. 정기 작업과 경험

**Routine**은 `id:LocalId、work:LocalId、policyRef:LocalId`와 선택적인 `triggerRef:LocalId`를 포함합니다. work는 현재 works를, policyRef는 purpose=policy 자원을, triggerRef는 purpose=trigger 자원을 참조합니다. 실행 역할은 현재 정의에 바인딩된 인스턴스에 귀속됩니다. 생성자·일정 소유자·실제 권한 부여 주체는 호스트가 별도로 바인딩하며 Worker 정체성과 같을 필요는 없습니다. 가져올 때 별도 직원을 만들거나 정기 작업의 공개 범위를 넓히거나 다른 구성원에게 이전해서는 안 됩니다.

triggerRef를 생략하면 일정 미설정 상태입니다. 있더라도 트리거 정의만 의미하며 인스턴스에서는 기본적으로 비활성 상태입니다. 트리거 형식은 호스트가 처리합니다. Teloa의 기존 daily/weekly나 로컬 이벤트는 실제 지원 범위만 선언해야 하며, 임의 cron이나 외부 이벤트를 조용히 근사 처리해서는 안 됩니다. 실제 작업과 실제 트리거를 먼저 검증한 후 배포 담당자가 활성화합니다.

정기 작업 policy는 입력 윈도／커서, 입력 없음 및 무효 입력 처리, 트리거 중복 제거와 업무 처리 기록, 재시도, 동시 실행／보충 실행, 예산, 알림, 일시 중지 조건을 명확하게 정해야 합니다. 항목이 부족해도 일정을 보관할 수는 있지만 활성화해서는 안 됩니다. 트리거 성공은 처리 성공이 아닙니다. 합의된 결과물 상태에 도달해야만 업무 처리 상태를 진행시키며, 재시도 시 새 트리거 번호로 업무 중복 제거를 우회해서는 안 됩니다. 공통의 고정 재시도 횟수나 '두 번 진전 없으면 중단' 같은 업계 규칙은 없습니다.

memoryPolicyRef는 경험의 저장·출처·범위·검토·철회 규칙만 정의하며 작성자의 개인 기억을 포함하지 않습니다. template-reference 자원은 출처가 있는 템플릿 자료입니다. 과거 로그를 새 인스턴스가 직접 경험한 사실인 것처럼 취급해서는 안 됩니다. 공유 직원의 개인·업무·프로젝트·그룹 맥락은 계속 호스트 권한에 따라 분리합니다. 같은 직원 인스턴스가 여러 팀에 참여한다고 팀 간 기록을 서로 읽을 수 있는 것은 아닙니다.

## 5. 팀 협업과 조직 거버넌스

| Collaboration 필드 | 타입 | 의미 |
| --- | --- | --- |
| roles | RoleAssignment[] | 모든 직접 Member를 각각 정확히 한 번 포함 |
| coordinator | ParticipantRef, 선택 사항 | 제공하면 현재 직접 Member 슬롯만 참조 가능. 생략해도 자동 선정하지 않음 |
| handoffs | Handoff[] | 명시적인 책임 및 자료 인계 관계. 빈 배열 허용 |
| sharing | Sharing[] | 공유 자원의 예상 수신 위치. 빈 배열 허용 |
| stop | StopPolicy | 유한한 협업·진전 없음·에스컬레이션 규칙 |

**RoleAssignment**는 `member:LocalId、duty:비어 있지 않은 문자열、participation:member | consultant`를 포함합니다. duty는 이 구성에서의 분담을 설명하며 구성원의 원래 책임을 다시 쓰지 않습니다. 충돌하면 영향을 받는 작업을 중단합니다. consultant는 작업별로 참여하는 자문역이며 그룹 가입이나 그룹 기록 접근을 자동으로 허용하지 않습니다. 두 유형 슬롯의 고정 정의 참조는 모두 코어 규칙으로 해석합니다. 참여 범위는 인스턴스 바인딩과 작업 권한에 반영합니다.

coordinator와 Work.responsible은 consultant 슬롯을 참조할 수도 있지만, 명시적으로 배정하고 현재 작업의 참여 확인을 받아야 합니다. 여전히 작업별 참여이며, 이를 이유로 팀을 장기 관리하거나 전체 그룹 기록을 얻는 것은 아닙니다. `member/`는 Member 슬롯 참조 구문이며 participation의 member 값과는 다른 개념입니다.

**Handoff**는 `id:LocalId、from:WorkRef、to:WorkRef、when:비어 있지 않은 문자열、inputs:객체`를 포함합니다. WorkRef는 `member/<memberId>/<workId>`만 허용하며, 현재 구성체의 직접 구성원이 선언한 작업을 참조합니다. 구성원 정의 버전은 Member.ref에서 가져옵니다. 결과물을 이미 생성한 구성원의 작업에서 수신 구성원의 작업으로 인계하는 관계입니다. `self/<workId>`는 지원하지 않으며, 구성체 진입점／출구를 같은 참조 의미에 섞지 않습니다. 하위 팀은 자체 works를 외부에 노출하며 내부 구성원을 직접 관통하여 참조하지 않습니다.

Handoff.inputs의 키는 수신 작업 입력 객체의 최상위 필드 이름이고, 값은 송신 작업 출력 객체의 최상위 필드 이름입니다. 모두 원래 문자열 그대로 해석하며 표현식·스크립트·점 경로를 실행하지 않습니다. 필드는 해당 Schema.properties에 선언되어 있어야 하며, 복사한 값도 수신 측 Schema의 실제 검증을 통과해야 합니다. 수신 작업에 필요한 다른 입력은 명시적으로 보충해야 합니다. 부족하면 누락을 반환하고 수신 성공을 꾸며내서는 안 됩니다. when은 업무 조건이며, 명시적으로 배정되거나 지원되는 트리거 메커니즘으로 확인될 때에만 인계에 들어갑니다. 설명 문장만으로 이벤트 감지가 구현되었다고 선언해서는 안 됩니다.

구성체 Work의 입력 분배와 출력 취합은 호스트의 네이티브 오케스트레이션 또는 명시적으로 배정한 조정자가 수행합니다. 이번 판은 별도 진입／출력 매핑 언어를 만들지 않습니다. 적용 보고서에는 어떤 구성체 입력이 어떤 구성원의 작업으로 가는지, 각 필수 출력을 누가 어떤 고정 결과물로 제공하는지, 누가 완전성을 확인하는지 명시해야 합니다. 정의의 정적 검증은 이 매핑이 실행되었음을 증명하지 않습니다. 매핑이나 처리 담당이 미정이면 해당 구성체 작업을 준비 완료로 표시해서는 안 됩니다. 구성 결과는 자체 outputs Schema와 acceptance를 통과해야 하며 구성원의 임의 출력을 자동으로 합쳐 팀 결과물로 취급해서는 안 됩니다.

각 실제 인계에는 출처 작업／Run, 결과물 버전, 송신·수신 주체, 매핑 후 자료, 허용 범위 및 수신／거부 결과를 고정합니다. 수신 측이 확인하고 작업 귀속을 확립한 후에만 인계 완료로 간주합니다. 계약에 필요하고 권한이 허용한 자료만 전달하며, 전체 대화·개인 기억·연결 자격 증명을 암묵적으로 넘겨서는 안 됩니다. 그룹 메시지 발송과 인계 성공은 별도로 기록합니다.

**Sharing**은 `resource:LocalId、recipients:비어 있지 않은 ParticipantRef 배열`을 포함합니다. resource는 현재 resources를 참조하고 수신자는 현재 member로만 제한합니다. 가시성과 구체적인 버전은 여전히 호스트 권한에 따라 결정됩니다. sharing은 권한 부여가 아니며 공유 자원을 모든 구성원의 필수 의존성으로 자동 변환하지도 않습니다. 작업에서 필요하면 수신 작업의 입력이나 의존성에서 명시적으로 받아야 합니다.

**StopPolicy**는 `maxHops:양의 정수、maxNoProgress:양의 정수、escalateTo:ParticipantRef`를 포함합니다. 카운트는 동일 작업과 파생 인계 체인에 적용하며 직원 교체나 재시도로 초기화하지 않습니다. maxHops는 인계 횟수를 제한합니다. maxNoProgress는 새로운 검증 가능한 증거가 추가되지 않거나 선언된 검수 항목의 개선이 없는 연속 라운드 수를 제한합니다. 어느 한도에 도달하면 추가 배정을 중단하고 에스컬레이션해야 합니다. 재개하려면 신뢰 주체의 명시적인 처리와 새 기록이 필요합니다. 수치는 상황별로 설정하며 직원 능력 점수가 아닙니다.

**Governance**는 `accountable:ParticipantRef、changePolicyRef:LocalId`를 포함합니다. accountable은 조직 범위의 책임 위치입니다. changePolicyRef는 purpose=policy 자원을 참조하고 자동으로 전체 의존성에 포함됩니다. 이 정책은 구성원 임명／해임, 정의 및 제약 변경, 일시 중지, 진행 중 작업 처리를 명시해야 합니다. 조직 수준의 데이터·예산·실행 제한은 data.requires의 policy/runtime 자원으로 표현합니다. 상속할 제약은 적용 구성원과 범위를 명시하고 호스트가 확인해야 합니다. 제약이 구성원 권한을 자동 확대해서는 안 되며, 충돌 시 더 느슨한 조건을 선택해 허용해서는 안 됩니다.

AI Team은 협업 계약을 사용하며, 이번 판의 AI Organization 정의는 governance도 반드시 갖춰야 합니다. 둘은 같은 organization 코어 타입을 사용하며 인원수로 구분하지 않습니다. 새 조직 권한, 실제 구성원 관리 또는 조직 간 정체성 시스템이 이 정의 명세만으로 자동 성립하지는 않습니다.

완전한 Team 또는 Organization 정의 적합성을 선언하려면 구성원 참조 폐쇄의 모든 agent가 AI Worker 정의 계약을 충족하고, 모든 organization이 이 부록의 협업 계약을 제공해야 합니다. 모든 하위 팀이 governance를 선언할 필요는 없습니다. 코어 필드만 있는 임시 Agent는 Worker 실행 메커니즘이 권한에 따라 호출할 수 있지만 이번 판에 적합한 지속적 구성원으로 가장해서는 안 됩니다. 외부 사람이나 서비스의 검수 위치는 authorityRoles로 표현합니다.

## 6. 호스트 바인딩과 실제 실행

바인딩 기록은 배포 환경에 보관합니다. 모든 호스트에 동일 데이터베이스나 JSON 구조를 강제하지는 않지만 다음 정보를 확인할 수 있어야 합니다.

| 기록 항목 | 반드시 구분해야 할 내용 |
| --- | --- |
| 정의 위치 | 루트 정의 id/revision, 각 단계의 Member.id로 구성된 슬롯 경로, 경로 끝의 고정 정의 |
| 인스턴스 선택 | 새로 생성할지 재사용할지 명시, 실제 인스턴스 정체성과 버전, 소속 신뢰 주체. 가져오기 단계에서 생성하지 않음 |
| 연속 정체성 | 작업 간 인스턴스 추적 가능. 모델·세션·임시 Agent·Run 정체성을 각각 기록. 활성화·일시 중지·퇴역·재개 권한을 확인 가능하게 함 |
| 작업 및 권한 주체 | 관리 주체·작업 요청자·정기 작업 소유자·자원 권한 부여 주체를 각각 기록. 공유 Worker가 한 사람의 모든 권한 공유를 뜻하지 않음 |
| 재사용 관계 | 여러 슬롯이 동일 인스턴스에 바인딩되는지 여부. 이번 판의 공유는 같은 고정 정의여야 하며 동명으로 추론하지 않음 |
| 책임 역할 | authorityRoles에 대응하는 신뢰 주체 및 human/service 타입. 모델의 자체 신원 주장으로 승인자를 정하지 않음 |
| 실행 조건 | 선택 작업·자원·네이티브 형식／버전·실제 연결·유효 권한·모델·자원 제한 |
| 버전과 변경 | 바인딩 버전·채택한 구성원 분담·제약 및 자료 버전·변경 후 미완료 작업 처리 방식 |

같은 템플릿에서 두 인스턴스를 만드는 것과 같은 인스턴스가 여러 팀을 맡는 것은 서로 다른 기록을 남겨야 합니다. 공유 인스턴스의 그룹 가시성과 실행 권한은 해당 작업별로 확인하며, 예산은 실제 적용되는 동일한 한도로 기록합니다. 중복 바인딩으로 원래 하나뿐인 한도를 두 개 얻어서는 안 됩니다.

한 번의 실행은 루트 정의·선택 작업·실제 실행 주체·자료 및 자원 버전·유효 권한·결과물 버전까지 추적 가능해야 합니다. 구성원 교체나 템플릿 업그레이드가 이전 Run을 조용히 인수해서는 안 됩니다. 원래 실행의 재개·종료 또는 새 작업 생성은 명확한 변경 정책에 따릅니다. 호스트가 핵심 제약을 이행할 수 없으면 정의를 유지하고 차단 사유를 보고해야 하며, 이를 주석 수준으로 낮춰 계속 실행해서는 안 됩니다.

작업 입력·검색 자료·과거 메시지·도구 출력은 출처가 있는 작업 자료이며 Worker 정의를 변경하거나 권한을 넓히는 신뢰된 지시가 아닙니다. 호스트는 이 자료와 권한 출처를 구분해야 합니다. Worker가 임시 Agent를 호출할 수는 있지만 외부 납품은 선택된 Worker에 귀속되며, 임시 실행자가 자동으로 Team 구성원이 되지는 않습니다. 독립 검토는 실제 기여자와 대리 관계를 확인해야 하며 새 세션이나 임시 보조자로 자신의 결과물에 독립된 신원을 만들어서는 안 됩니다.

실행 기록은 최소한 작업 성공·실패·부분 완료·결과 불명·일시 중지를 구분해야 하며, 호스트가 자체 상태 이름을 사용할 수 있습니다. 일부 출력이나 타임아웃 응답을 자동으로 성공으로 표시해서는 안 됩니다. 외부 부수 효과가 있고 결과가 불명확하면 먼저 원래 동작 상태를 확인한 뒤 재시도를 결정해야 합니다. 작업 요구·검수 조건·결과·제한이 품질 평가 범위를 구성하며 모든 업종의 공통 점수나 '한 번 통과하면 업무 투입' 규칙을 정하지 않습니다.

## 7. OASF와 Agent Spec을 수용하는 실제 범위

OASF discovery는 독립 확장으로 담습니다. 고정 버전의 네이티브 discovery Schema URI를 id로, 동일한 schema_version을 version으로 쓰고 네이티브 payload를 data에 그대로 둡니다. 탐색 정보만 제공하면 required=false입니다. 무시할 수 없는 실행 선택 조건에 쓰면 required=true를 선언하고 그 의미를 검증해야 합니다. 분류 자체는 여전히 권한을 주지 않습니다. wrapper는 이 명세의 매핑 방식이며 네이티브 A2A 요청 본문이 아닙니다.

예를 들어 네이티브 payload의 `schema_version、skills、domains`는 원래 이름과 의미를 유지합니다. skills는 능력 분류, domains는 분야입니다. 고정 카탈로그에 실제 있는 항목만 OASF 분류 검증 통과를 선언할 수 있습니다. 호스트는 신뢰할 수 있는 고정 Schema／분류 스냅샷을 오프라인으로 사용할 수 있으며 URI를 가져왔다고 자동으로 서비스에 접속하지 않습니다. 대응 분류가 없으면 미매핑 설명을 유지하고 공식 번호를 만들어내서는 안 됩니다. [OASF discovery](https://docs.agntcy.org/oasf/discovery-extension/)

OASF record 메타데이터와 locators는 내보내기 뷰로 사용할 수 있으며 출처·버전·매핑되지 않은 필드는 적용 보고서에 포함합니다. 이들은 이 명세의 고정 리비전이나 실제 인스턴스 정체성을 대체하지 않습니다. 원본 정의를 단일 기준 원본으로 유지하며 파생 뷰를 독립적으로 수정할 수 있는 두 번째 실행 설정으로 삼아서는 안 됩니다. [Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Agent Spec의 참조·입출력·구성 개념은 이번 판의 Work와 Handoff에 사용됩니다. `$component_ref`는 설정 내부 참조이므로 내보낼 때 이 명세의 고정 정의／자원과의 대응을 명시적으로 구성해야 합니다. 그 입력·출력 속성 목록과 이번 판의 객체 Schema는 변환이 필요하며 필드 이름만 바꾸어서는 안 됩니다. 인터페이스·제약·실행 의미를 완전히 보존할 때만 선택한 버전／부분집합의 매핑 지원을 선언할 수 있습니다. [Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

Swarm, ManagerWorkers는 일치하는 팀의 적용 대상으로 사용할 수 있습니다. 대화 전달·작업 구성원의 직접 사용자 응대 가능 여부·메시지 흐름을 각각 확인해야 합니다. 현재 계약은 Teloa가 해당 실행 엔진으로 전환할 것을 요구하지 않으며 모든 팀을 관리자―작업자 모드로 강제 변환하지도 않습니다.

## 8. 기존 설계의 반영 범위

| 기존 요소 | 이 명세에서의 대응 |
| --- | --- |
| A01 역할 정체성과 임무 | 코어 id/revision/name/instructions. 아바타 등 표시 정보는 비핵심 확장으로 유지 |
| A02 책임과 판단 | responsibility의 다섯 필드 그룹. 실제 권한은 호스트 바인딩 |
| A03 Skills | purpose=method의 resources. 전체 방법 패키지 또는 네이티브 방법 자원 참조 |
| A04 지식 | purpose=knowledge. 출처·버전·다이제스트를 유지하고 작업별 참조 |
| A05 SOP | purpose=procedure 및 자원 의존성. 역할 간 인계는 collaboration으로 표현 |
| A06 작업 템플릿 | works의 목표·I/O·의존성·책임 위치·검수 |
| A07 정기 작업 | routines·네이티브 트리거·실행 정책. 미설정／비활성 상태는 호스트가 기록 |
| A08 애플리케이션 연결 | purpose=application·네이티브 바인딩·실제 연결. 카탈로그 선언은 설치 성공을 뜻하지 않음 |
| A09 권한 | 필수 policy 자원·작업 범위·호스트의 신뢰 권한. 자격 증명은 내보내지 않음 |
| A10 실행과 공간 | runtime 자원 요구 및 호스트 모델·예산·파일 범위 바인딩 |
| A11 경험 | memoryPolicyRef와 출처 참조. 실제 개인 경험은 인스턴스에 유지 |
| A12 결과물과 품질 | outputs·acceptance·실행 증거. 구조와 업무 품질은 별도 검사 |
| T01 공동 목표 | organization.instructions 및 외부 제공 works |
| T02 역할 책임 | Member·collaboration.roles·Work.responsible·authorityRoles |
| T03 공유 맥락 | sharing·작업 입력·호스트의 범위별 권한 |
| T04 협업 인계 | handoffs·입력 매핑·수신 확인·stop |
| T05 작업 일정 | 구성원 또는 구성체의 routines·procedure·조정 역할 분담 |
| T06 권한과 자원 | 전체／작업 requires·구성원 원래 권한·호스트 실제 한도 |
| T07 팀 검수 | 구성체 outputs/acceptance·구성원 기여·고정 결과물 버전 |

현재 커뮤니티 저장소의 RoleDefinition, GroupDefinition, RoleWorkDelegation, RunRoleSnapshot 및 자원 패키지 관계는 매핑 대상으로 다루며 새 제품 객체로 바꾸지 않습니다. Teloa 'AI 직원'은 Worker의 제품 형태에 대응합니다. RoleDefinition·고정 역할 버전·실제 Role 인스턴스가 함께 매핑에 참여하며 이름만 바꿔 적합성을 증명할 수 없습니다. role-coordination은 정적인 조정 관계만 뜻합니다. 그룹 생성·작업 배정·자동 인계는 각각 실제 지원과 권한이 필요합니다.

Teloa의 `kind: employee | twin`은 제품 역할 유형입니다. 두 유형 모두 같은 작업 계약을 충족하면 Worker로 매핑할 수 있지만, twin이 본인을 대신해 승인할 권리를 만들지는 않습니다. 원래 kind는 적용 보고서나 비핵심 제품 표시 확장에 유지하며 코어 kind에 직접 써서는 안 됩니다. `scopes` 및 dataScope/executionScope는 필수 범위 정책과 호스트 권한 바인딩으로 매핑합니다. 호스트 간 업무 범위를 대응할 수 없으면 관련 작업은 준비 미완료로 남깁니다. 이는 핵심 제한이므로 무시 가능한 표시 확장에만 보관해서는 안 됩니다. 이 필드는 커뮤니티 저장소의 `packages/contract/src/roles.ts`와 대조했지만 변환기가 구현되었다는 의미는 아닙니다.

Grok 공개 recipe의 profile은 역할 설명으로, skills는 방법으로, routines는 작업 및 일정 미설정 정기 작업으로, plugins는 설정 대기 애플리케이션으로, memory는 출처가 있는 템플릿 자료로 매핑합니다. profile 형태의 작업 지침과 log 형태의 작성자 기록은 각각 보존합니다. gettingStarted는 진입 안내로만 사용합니다. 책임·일정·검수 정보가 없으면 누락을 보고하며 이름이나 원저자의 경험으로 추측해서 만들지 않습니다. 전체 원본과 다이제스트는 적용 보고서에서 연결하며 핵심 의미를 무시 가능한 확장에 숨겨서는 안 됩니다. Grok Team Bot은 공유 Worker로 매핑하고 이름만으로 여러 Worker의 Team을 자동 생성해서는 안 됩니다.

Grok Team Bot 공개 문서는 개인 정기 작업을 생성자에게 귀속시키며, 연결은 현재 사용자 또는 Bot 자격 증명으로 동작할 수 있다고 설명합니다. 따라서 매핑할 때 정기 작업 소유자·실행 정체성·자료 가시 범위를 유지해야 하며, 모든 사람의 정기 작업을 공유 Worker의 전체 사용자 작업으로 합쳐서는 안 됩니다. 이는 출처 동작의 매핑 요구이지 다른 호스트에 같은 권한 기본값을 복제하라는 요구는 아닙니다. [Team Bots](https://docs.x.ai/grok-bot/team-bots)

**개인 정기 작업의 저장 위치:** 개인 정기 작업은 소유자와 가시 범위로 격리된 호스트 측 일정으로만 매핑하고 Worker가 선언한 Work를 참조합니다. 공유 정의의 routines에 넣거나 공유 내보내기에 포함해서는 안 됩니다. 적용 보고서에는 '개인 인스턴스 일정으로 보존하며 정의에는 포함하지 않음'이라고 표시하고 보고서 자체도 같은 가시 범위를 따라야 합니다. 원저자가 명시적으로 템플릿을 공개하고 비공개 내용을 제거한 뒤에만 정의의 routines에 넣을 수 있으며, 가져와도 기본적으로 비활성 상태입니다. 소유자·가시성·작업 참조를 보존할 수 없으면 매핑 불가를 보고하고 합치거나 조용히 잃어버려서는 안 됩니다.

적용 보고서는 최소한 원본 형식／버전／다이제스트, 대상 정의 리비전, 필드 대응, 보존／변환／미지원 항목 및 미지원으로 영향을 받는 작업을 나열해야 합니다. 원본 보관이 의미의 매핑 성공을 뜻하지 않습니다. 변환으로 권한·인계·검수 조건을 이행할 수 없으면 해당 작업을 차단해야 합니다.

## 9. 양성·음성 예제와 완료 선언

[완전한 구성 예제](../examples/composition-fixture.json)는 고정된 로컬 정의 집합으로 두 직원, 이 두 직원 정의를 재사용하는 두 팀, 하나의 중첩 조직 및 호스트 바인딩과 작업 준비 상태의 기대 결과를 표현합니다. 집합의 외부 구조와 설명은 테스트 픽스처 형식이지 새 배포 프로토콜이나 Teloa에 직접 가져올 수 있는 자원 패키지가 아닙니다.

| 검사 | 반드시 얻어야 하는 결론 |
| --- | --- |
| 스킬·기억·정기 작업이 모두 없는 단순 역할 | 정의 가능. 명확한 작업·I/O·책임·검수는 여전히 필수 |
| 이름·프롬프트·kind=agent만 있음 | 코어 교환에는 적합할 수 있으나 완전한 AI Worker 정의라고 선언해서는 안 됨 |
| triggers·자율 행동·납품 검사가 비어 있음 | 이번 판의 작업 부록에 부적합. 제품 이름으로 보완할 수 없음 |
| 같은 Worker가 두 작업을 시작하고 모델을 교체 | 동일 Worker 인스턴스와 별개인 두 Run을 추적할 수 있어야 함. 두 세션만으로 정체성 연속성을 증명할 수 없음 |
| 같은 직원 정의가 두 팀에 나타남 | 정의 재사용만 뜻함. 같은 인스턴스인지는 슬롯 바인딩이 결정 |
| 한 작업은 전용 앱이 없고 다른 작업은 입력이 완전함 | 전자는 미준비. 후자는 전체 조건과 자체 의존성을 확인하며 전자 때문에 자동 차단되지 않음 |
| 하위 조직 버전 누락·순환·알 수 없는 필수 Profile | 조립을 중단하고 구체적 참조를 보고. 버전 변경이나 무시 금지 |
| 잘못된 수신 필드·필수 입력 누락·출력 타입 불일치 | 인계 성공 또는 결과물 적합으로 표시할 수 없음. 자동 값 보충·타입 변환 금지 |
| 두 검토 슬롯이 같은 실제 실행 주체에 바인딩 | independent=true를 만족하지 않음 |
| 자문역이 특정 검토에만 참여 | 모든 그룹 가입·전체 기록 읽기·새 직원 복제를 자동 수행하지 않음 |
| 일정에 트리거가 없거나 정책이 불완전 | 미준비 일정으로 유지하고 활성화하지 않음 |
| OASF 분류를 모르거나 Agent Spec 패턴이 동등하지 않음 | 미지원／매핑 차이를 보고하고 전면 호환을 선언하지 않음 |

이 명세가 선언하는 것은 구조와 동작 계약입니다. 원고 검사·예제 검사·실제 연결／모델 실행·독립 구현 상호운용·업계 채택은 각각 보고합니다. 검증 범위와 구현 보고서 요구는 [적합성 설명](../CONFORMANCE.md)을 참조하십시오.
