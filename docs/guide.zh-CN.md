# AI Worker：一个员工怎样工作，一支团队怎样交付

[Languages / 语言](languages.md)

**Max Luo、Morgan Chen｜Teloa 联合创始人** · 2026 年 10 月 18 日

在 Teloa 里，用户创建和协作的工作个体叫 **AI 员工**。**AI Worker 是背后的通用标准概念**：用持续身份、职责、工作合同和协作边界，描述一个 AI 员工怎样工作。产品中的 AI 员工，以及它所属的 AI 团队，都可以用这套标准来说明组成与交付要求。

给 AI 员工一个名字、写一段岗位提示词，已经可以开始试用。但第二次交办工作时，问题会变得具体：它还是上次那个员工吗？本次用了哪些材料？它把什么交给了下一位成员？报告经过复核以后，谁决定采用？

AI Worker 标准把这些约定写清楚，让使用者能够核对 AI 员工承担了什么、交付了什么，也让不同产品有共同的技术表达。

本文介绍 **AI Worker 标准 1.0**，包括核心规范和工作与协作应用规范。文中的例子是教学材料，不是客户案例或运行证明。[规范正文](../spec/core.zh-CN.md)规定技术要求。

三个核心概念可以先这样区分：

| 概念 | 定义 | 回答的问题 |
| --- | --- | --- |
| **AI Worker** | 具有持续身份，在明确授权边界内承担职责、接受工作并交付可验收成果的 AI 工作个体 | 这位 AI 员工是谁，负责什么，怎样证明完成？ |
| **AI Team** | 围绕共同成果，明确成员分工、材料交接与验收要求的协作组合 | 多位 AI 员工怎样共同完成一项工作？ |
| **AI Organization（AI Org）** | 在个体与团队的组合上，增加组织责任、资源与信息边界及变更治理的组织 | 多支团队由谁负责，怎样分配资源和管理变化？ |

“持续身份”是跨任务可以识别同一个工作者，不要求永久在线、独占机器或长期记忆。“负责”表示工作归属与可追溯性，不赋予 AI 法律人格。下文用正文、表格和步骤说明这些关系，配图提供同一内容的视觉概览。

## 01 一个 AI 员工，需要把哪些事情说清楚

以负责材料摘要的 AI 员工为例。它负责根据给定材料写摘要，材料没有提供的事实要留下问题。它可以反复承担这个岗位，具体任务可以使用不同模型。每轮结果仍归属于同一个 AI 员工；技术上，它对应一个固定的 Worker 实例，并记录采用的定义版本。

![Teloa AI 员工、Grok Bot 与 AI Worker 的概念对应及五组组成](../diagrams/zh-CN/worker.png)

*Teloa AI 员工、Grok Bot 与 AI Worker 的概念对应及五组组成。*

图中的箭头表示概念对应：Teloa 保留 AI 员工这一产品概念，Grok 保留 Bot。它们可以用 AI Worker 的共同定义来说明；图示本身不表示已完成适配或获得厂商认证。

**AI 员工的五组组成**说明岗位需要约定什么；其中的资源按实际工作选择，不要求每位员工装齐所有工具。

| 组成 | 通用含义 | 材料摘要 AI 员工的具体配置 |
| --- | --- | --- |
| **岗位与职责** | 持续身份、岗位使命、职责边界，以及自主判断、确认和升级规则 | 摘要已有材料；发现矛盾时列出，不替作者补造事实 |
| **方法与依据** | Skill 提供做事方法，知识提供判断材料，SOP 说明步骤、检查点与异常处理；分别保留来源与版本 | 使用本轮输入材料；复杂工作再追加 Skill、知识或 SOP |
| **工作与安排** | 工作合同规定目标、输入、输出、依赖、负责位置和验收；例行任务约定何时调用哪项工作 | 提供 `summarize` 工作入口；收到任务时执行，暂不设例行 |
| **执行条件** | 应用与工具需求、资料范围、有效授权，以及模型、预算和运行空间等条件 | 只读取获准提供的材料；对外发布另行确认 |
| **经验与成果** | 记忆规则说明经验如何保存、使用与撤回；成果和证据固定版本，并按要求验收 | 输出摘要和未决问题；任务负责人检查与原文是否一致 |

这里没有强制配置记忆库、应用连接或定时计划。资源是否必要，取决于承诺的工作。如果要查询外部资料，就必须把连接和授权列为条件；如果只摘要输入文本，就不必为了凑齐模块而增加工具。

一个完整 Worker 定义至少要有身份与修订、职责与判断边界，以及一项说明输入、输出、负责位置和验收要求的工作。实际使用还需要宿主绑定具体实例、运行条件与可信授权。五组组成是阅读方式，覆盖身份、责任、Skills、知识、SOP、工作模板、例行任务、应用、权限、运行条件、经验、成果与质量等要素；具体字段见[工作与协作应用规范](../spec/work-profile.zh-CN.md)。

## 02 团队交付要能追到每次交接

假设一组人希望 AI 完成“整理资料并检查结论”。分析 AI 员工读取材料，复核 AI 员工检查证据，团队交付报告与复核意见。建立群聊可以方便交流；团队合同还要把共同成果、成员分工、交接条件和停止规则写清楚。

**AI Team 的组成是：共同目标＋成员与岗位分工＋共享上下文边界＋协作交接＋工作安排＋资源约束＋成果验收。**

| 团队要素 | 需要说清楚的约定 |
| --- | --- |
| 共同目标 | 团队对外接受什么工作，最终交付什么成果 |
| 成员与岗位分工 | 各成员负责什么；常驻成员与按任务参与的顾问分别如何参与 |
| 共享上下文 | 哪些资料可交给哪些成员，采用哪个版本，不默认共享全部会话或私人记忆 |
| 协作交接 | 谁把哪个固定成果交给谁，怎样映射输入，接收方如何确认或拒收 |
| 工作安排 | 谁承担输入分发与输出汇总；由宿主编排还是明确交办的协调者处理 |
| 资源约束 | 每项工作的授权、应用、预算及停止条件；无进展时向谁升级 |
| 成果验收 | 检查哪些输出，由谁验收哪个版本，是否要求独立复核 |

协调者是可选角色，不要求所有团队都采用主管制。成员名单、群聊和组织图也不能代替这些工作约定。

组合本身也有工作接口。例如团队的 `deliver` 接收 `evidence`，必须交付 `report`、`evidence` 和 `review`。协调者或宿主需要说明：输入交给谁，三个输出分别来自哪个固定成果，由谁检查是否齐全。缺少这些对应关系时，团队工作仍未就绪。

![Teloa AI 员工按 Team 合同协作，人负责审批与验收](../diagrams/zh-CN/delivery.png)

*Teloa AI 员工按 Team 合同协作，人负责审批与验收。*

图中的示例流程分为六步：

1. **人类负责人明确交办。** 给出目标、输入与授权范围，选择团队工作入口，确定交付和验收要求。
2. **宿主或协调者校验并分发。** 检查合同、依赖和实例绑定，只分发获准材料，并建立实际任务归属。
3. **分析 AI 员工提交成果。** 执行已交办工作，固定报告与证据版本，记录实际贡献者。
4. **复核 AI 员工确认接收并复核。** 核对输入，接收后完成检查并固定复核意见；拒收时记录原因，交回协调处理。
5. **宿主或协调者检查成果齐全。** 按团队合同汇总固定来源，检查必需输出，保留贡献者和交接记录。
6. **人类负责人验收并决定采用。** 验收指定成果版本，另行记录是否用于业务；通过验收不自动批准对外动作。

这里采用“分析、复核、人工验收”的示例分工；具体团队按自己的合同安排。跨环节保持同一条证据链：**获准输入 → 固定报告 → 复核意见 → 最终成果包**。

成员间的一次交接可以写成下面的合同片段，取自[完整组合示例](../examples/composition-fixture.json)：

```json
{
  "id": "review-report",
  "from": "member/analyst/inspect",
  "to": "member/quality/review",
  "when": "已有固定报告与证据且获得本项交接授权",
  "inputs": {
    "report": "report",
    "evidence": "evidence"
  }
}
```

`inputs` 左侧是接收方字段，右侧是发送方输出字段。这段定义不发送消息，也不执行派工。真正交接时，还要记录发送人与接收人、来源 Run、成果版本、获准传递的材料，以及接收或拒收结果。消息发到了群里，不等于接收方已经拿到可用输入。

图中复核 AI 员工产出的是复核意见；完整成果包仍由指定负责人验收。独立验收要检查实际贡献者。若复核人改写了报告，新的报告也包含其贡献，不能继续把这个人视为该版本的独立验收者。

## 03 AI Org 在团队之上补充什么

组织可以组合多个团队和工作者，并约定跨团队的责任、资源限制与变更规则。增加人数或再建一层群，不会自动形成这些约定。

**AI Org 的组成是：个体和团队的组合＋跨团队责任＋资源与信息边界＋升级与变更规则。**

| 组织要素 | 对已有团队补充什么 |
| --- | --- |
| 个体与团队的组合 | 列明成员和固定定义版本；子团队通过自己的工作接口参与，不自动暴露全部内部能力 |
| 跨团队责任 | 明确对组织范围负责的可信主体，以及跨团队问题的升级去向 |
| 资源与信息边界 | 规定数据、预算和执行限制适用于哪些成员，由宿主核对和执行 |
| 升级与变更规则 | 规定成员任职与撤任、定义变更、暂停恢复，以及在途工作的处理方式 |

![以 Teloa AI 员工为例，说明 Worker、AI Team 与 AI Org 的组合](../diagrams/zh-CN/composition.png)

*以 Teloa AI 员工为例，说明 Worker、AI Team 与 AI Org 的组合。*

例如，一个安全运营组织可以由研判调查团队和检测工程团队组成，共用一名质检 AI 员工。共用需要绑定同一个实际实例，不能只因为两个位置引用同一岗位模板就推断是同一个员工。

组织还要说明谁对组织范围负责，谁决定成员任职或撤任，员工暂停以后在途工作怎样处理，以及哪些资料和预算限制适用于哪些成员。同一个员工参与两支团队，不代表两边历史可以互读，也不产生两份原本只有一份的预算。

这是一种可表达的组织结构。是否已在某个产品执行，需要该产品提供绑定、授权和运行证据。图中场景与下载的结构夹具不同：夹具的 A、B 两组同时复用分析和质检员工，用于说明实例绑定，未配置真实检测工程岗位。

## 04 技术上分清定义、实例和一次执行

Worker 定义像 AI 员工的岗位说明和工作合同；Worker 实例对应 Teloa 中一位具体的 AI 员工；Run 是这个员工的一次执行。岗位模板升级，旧 Run 仍保留原版本。更换模型，也不必把员工历史变成另一个人的历史。

![以 Teloa 为例：Worker 定义、AI 员工实例、Run 与成果验收](../diagrams/zh-CN/architecture.png)

*以 Teloa 为例：Worker 定义、AI 员工实例、Run 与成果验收。*

**技术链路是：标准定义 → 合同校验 → 宿主绑定 → 一次 Run → 固定成果 → 验收记录 → 业务采用。** 各环节分别回答不同问题：

| 层次 | 对象或环节 | 记录和检查的内容 |
| --- | --- | --- |
| 标准定义 | 核心定义与工作扩展 | `id`、`revision`、`kind` 与成员固定引用；职责、工作输入输出、依赖、协作和验收要求 |
| 宿主配置 | 合同与能力校验 | 引用是否存在、输入输出合同是否完整、必要能力是否受支持；缺项时将受影响工作标为未就绪 |
| 宿主配置 | Worker 实例与绑定 | 具体 AI 员工的持续身份，以及本项工作的资料、模型、应用连接和有效授权 |
| 实际执行 | Work、任务与 Run | Work 是可重复调用的工作合同；任务是一次具体交办；Run 记录一次执行的输入、定义版本和实际执行主体 |
| 工作交付 | 固定成果 | 可查看的成果内容、版本、证据和实际贡献者，而不只是“运行结束”状态 |
| 工作交付 | 验收记录 | 谁依据哪些要求检查了哪个成果版本，以及检查结论；要求独立时还需核对实际贡献者 |
| 业务决定 | 采用记录 | 负责人是否决定使用该成果；采用与验收分别记录，不自动授予发布或处置权限 |

例如，“材料摘要岗位第 2 修订”是一份定义；按它创建的“资料整理员”是一位实例；本周摘要和下周摘要是两项任务，各自保留 Run 与成果。更新岗位模板不回写旧 Run，也不把旧成果署名转给新员工。

核心格式只保留 `agent` 与 `organization`。Worker 使用 `agent` 加必需工作扩展，Team 使用 `organization` 加协作合同，Org 再增加治理合同。这样可以沿同一套引用和版本规则组合，无需为每种产品称呼另造文件类型。

宿主是实际运行这些定义的平台，例如 Teloa。它负责把定义绑定到真实实例、资料、工具连接、模型与授权主体，检查输入和依赖，并记录运行和成果。导入文件只带来一份待解释的定义，不会自动连接账号、授予权限、启动执行或启用例行。结构校验、配置就绪、执行成功、成果验收和业务采用需要各自的证据，不能互相代替。

## 05 一个可以逐字段核对的例子

[材料摘要 Worker](../examples/document-worker.json)是一份完整 JSON 定义，包含全部必需字段。它的 `summarize` 接受一个非空 `material` 字符串，输出非空 `summary` 和字符串数组 `openQuestions`。以下输入输出是手写的教学示例：

```json
{
  "material": "示例周报：甲项目本周完成三份资料摘要。第二份缺少来源日期，负责人要求补充。材料没有提供工时或客户反馈。"
}
```

```json
{
  "summary": "甲项目本周完成三份资料摘要，其中第二份仍需补充来源日期。",
  "openQuestions": [
    "第二份资料的来源日期是什么？",
    "现有材料未提供工时或客户反馈，无法据此评价效率或满意度。"
  ]
}
```

结构检查能发现缺字段和错误类型。负责人还要检查内容：是否忠于材料，是否把没有工时数据的情况写成“效率提升”。验收针对固定输出版本；修改以后，需要按约定重新检查。

换成 SOC 研判，仍可复用这种关系。假设教学材料只包含一条 WAF 的 HTTP 403 记录，那么报告只能解释这条记录支持什么结论，并注明缺少后端和终端证据。它不能据此断言服务器已经失陷，也不能断言完全安全。更深调查需要哪些数据，写成明确缺口；封禁、隔离等处置需要相应工具与授权。这一例子没有连接真实环境或执行攻击。

## 06 Grok Bot 与 Teloa 怎样对应

Teloa 的 AI 员工是 AI Worker 在产品中的具体表达，Grok Bot 也可以按 AI Worker 来描述。AI 员工、Bot 是各自的产品概念；AI Worker 提供共同的技术定义，适配时再逐项核对职责、工作合同与宿主行为。Grok 的公开设计介绍了可持续存在的 Bot，以及 Skills、Routines 等组成；这支持概念上的比较，不等于已有转换器或官方兼容认证。[Grok 设计说明](https://x.ai/news/designing-grok-bot)

| 产品概念 | 在本规范中的对应 | 适配时需要确认 |
| --- | --- | --- |
| Teloa AI 员工；Grok Bot | Worker 定义与实际实例 | 持续身份、职责、工作 I/O 和验收是否完整 |
| 岗位提示词、Bot profile | `instructions` 与 `responsibility` | 工作边界是否具体，缺项不得从名字推断 |
| Skills、知识、SOP | 按用途引用的 `resources` | 真实版本、来源与工作依赖 |
| 工具或插件 | 能力引用、应用资源与宿主连接 | 实际授权，凭据留在宿主 |
| Teloa 群与项目 | 团队沟通和上下文载体 | 还需明确分工、交接和团队成果合同 |
| Grok Team Bot | 共享 Worker | 使用者的授权、私人会话与私人例行分别保留 |

Grok Team Bot 的文档描述的是多人使用同一个 Bot。它与“多个 Worker 分工完成一份成果”的 AI Team 不同。适配共享 Worker 时，个人例行保留在宿主的私人安排中，不进入共享定义；只有作者明确发布并移除私有内容的模板才能被分享，导入后仍不自动启用。[Team Bots](https://docs.x.ai/grok-bot/team-bots)

更细的 Teloa 字段对应与适配缺项见[映射文档](mappings.md)。

## 07 复用现有规范，保持范围清楚

OASF 提供 Agent 的发现记录、领域与能力分类，适合帮助使用者找到候选能力。本规范保留这些原生分类及其版本，另用工作合同说明输入、输出与验收。OASF 的分类技能和可执行 Skill 包不是同一种对象。[OASF Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Oracle Agent Spec 的组件引用、输入输出与组合定义值得复用。本规范借鉴这些思路；适配具体版本时仍须逐项转换接口、引用和执行语义，不能把字段改名就称为互通。[Oracle Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

JSON 用于交换固定定义，YAML 可以用于编写。YAML 转换须拒绝重复键、锚点、别名、显式标签、非有限数值和多文档等不在约定内的输入，并保留数值与字符串含义。例如 `revision: "1"` 是字符串，`revision: 1` 会因类型错误被拒绝。两种文件不能成为同一修订下各自随意修改的来源。

## 08 怎样开始采用

选一项已有工作，先写清输入、输出、依赖、负责位置和验收。用真实实例执行后，检查接收方实际取得的材料与固定成果，再扩大到团队。如果当前平台无法兑现某项关键约束，就把相应工作标为未就绪。

本版希望先把这些关系定义清楚。要成为可由行业共同采用的规范，还需要独立实现的互操作证据、非 SOC 场景，以及公开的变更讨论。仓库采用 Apache-2.0 许可，欢迎从一个具体歧义或反例开始参与。[标准仓库](https://github.com/teloa-ai/ai-worker-standard) · [反馈入口](https://github.com/teloa-ai/ai-worker-standard/issues)
