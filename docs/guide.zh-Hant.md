# AI Worker：一個員工怎樣工作，一支團隊怎樣交付

[Languages / 语言](languages.md)

**Max Luo、Morgan Chen｜Teloa 共同創辦人** · 2026 年 10 月 18 日

> 本文是[簡體中文權威版本](guide.zh-CN.md)的完整繁體中文譯文，尚未經母語業界專家完整複核。如有歧義或衝突，以簡體中文版為準；歡迎回報翻譯問題。JSON／YAML 範例保留原始中文值，以確保各語言的範例相同。配圖沿用簡體中文版，正文提供完整的繁體中文說明。

在 Teloa 裡，使用者建立和協作的工作個體叫 **AI 員工**。**AI Worker 是背後的通用標準概念**：用持續身分、職責、工作契約和協作邊界，描述一個 AI 員工怎樣工作。產品中的 AI 員工，以及它所屬的 AI 團隊，都可以用這套標準來說明組成與交付要求。

給 AI 員工一個名字、寫一段職務提示詞，已經可以開始試用。但第二次交辦工作時，問題會變得具體：它還是上次那個員工嗎？本次用了哪些材料？它把什麼交給了下一位成員？報告經過複核以後，誰決定採用？

AI Worker 標準把這些約定寫清楚，讓使用者能夠核對 AI 員工承擔了什麼、交付了什麼，也讓不同產品有共同的技術表達。

本文介紹 **AI Worker 標準 1.0**，包括核心規範和工作與協作應用規範。文中的例子是教學材料，不是客戶案例或執行證明。[規範正文](../spec/core.zh-Hant.md)規定技術要求。

三個核心概念可以先這樣區分：

| 概念 | 定義 | 回答的問題 |
| --- | --- | --- |
| **AI Worker** | 具有持續身分，在明確授權邊界內承擔職責、接受工作並交付可驗收成果的 AI 工作個體 | 這位 AI 員工是誰，負責什麼，怎樣證明完成？ |
| **AI Team** | 圍繞共同成果，明確成員分工、材料交接與驗收要求的協作組合 | 多位 AI 員工怎樣共同完成一項工作？ |
| **AI Organization（AI Org）** | 在個體與團隊的組合上，增加組織責任、資源與資訊邊界及變更治理的組織 | 多支團隊由誰負責，怎樣分配資源和管理變化？ |

「持續身分」是跨任務可以辨識同一個工作者，不要求永久保持連線、獨佔機器或長期記憶。「負責」表示工作歸屬與可追溯性，不賦予 AI 法律人格。下文用正文、表格和步驟說明這些關係，配圖提供同一內容的視覺概覽。

## 01 一個 AI 員工，需要把哪些事情說清楚

以負責材料摘要的 AI 員工為例。它負責根據給定材料寫摘要，材料沒有提供的事實要留下問題。它可以反覆承擔這個職務，具體任務可以使用不同模型。每輪結果仍歸屬於同一個 AI 員工；技術上，它對應一個固定的 Worker 實例，並記錄採用的定義版本。

![Teloa AI 員工、Grok Bot 與 AI Worker 的概念對應及五組組成](../diagrams/zh-CN/worker.png)

*Teloa AI 員工、Grok Bot 與 AI Worker 的概念對應及五組組成。*

圖中的箭頭表示概念對應：Teloa 保留 AI 員工這一產品概念，Grok 保留 Bot。它們可以用 AI Worker 的共同定義來說明；圖示本身不表示已完成適配或獲得廠商認證。

**AI 員工的五組組成**說明職務需要約定什麼；其中的資源按實際工作選擇，不要求每位員工裝齊所有工具。

| 組成 | 通用含義 | 材料摘要 AI 員工的具體設定 |
| --- | --- | --- |
| **職務與職責** | 持續身分、職務使命、職責邊界，以及自主判斷、確認和升級規則 | 摘要已有材料；發現矛盾時列出，不替作者補造事實 |
| **方法與依據** | Skill 提供做事方法，知識提供判斷材料，SOP 說明步驟、檢查點與異常處理；分別保留來源與版本 | 使用本輪輸入材料；複雜工作再追加 Skill、知識或 SOP |
| **工作與安排** | 工作契約規定目標、輸入、輸出、依賴、負責位置和驗收；例行任務約定何時呼叫哪項工作 | 提供 `summarize` 工作入口；收到任務時執行，暫不設定例行任務 |
| **執行條件** | 應用與工具需求、資料範圍、有效授權，以及模型、預算和執行空間等條件 | 僅讀取獲准提供的材料；對外發佈另行確認 |
| **經驗與成果** | 記憶規則說明經驗如何保存、使用與撤回；成果和證據固定版本，並按要求驗收 | 輸出摘要和未決問題；任務負責人檢查與原文是否一致 |

這裡沒有強制設定記憶庫、應用連線或定時計劃。資源是否必要，取決於承諾的工作。如果要查詢外部資料，就必須把連線和授權列為條件；如果只摘要輸入文字，就不必為了湊齊模組而增加工具。

一個完整 Worker 定義至少要有身分與修訂、職責與判斷邊界，以及一項說明輸入、輸出、負責位置和驗收要求的工作。實際使用還需要宿主綁定具體實例、執行條件與可信授權。五組組成是閱讀方式，覆蓋身分、責任、Skills、知識、SOP、工作範本、例行任務、應用、權限、執行條件、經驗、成果與品質等要素；具體欄位見[工作與協作應用規範](../spec/work-profile.zh-Hant.md)。

## 02 團隊交付要能追到每次交接

假設一組人希望 AI 完成「整理資料並檢查結論」。分析 AI 員工讀取材料，複核 AI 員工檢查證據，團隊交付報告與複核意見。建立群組聊天可以方便交流；團隊契約還要把共同成果、成員分工、交接條件和停止規則寫清楚。

**AI Team 的組成是：共同目標＋成員與職務分工＋共享上下文邊界＋協作交接＋工作安排＋資源約束＋成果驗收。**

| 團隊要素 | 需要說清楚的約定 |
| --- | --- |
| 共同目標 | 團隊對外接受什麼工作，最終交付什麼成果 |
| 成員與職務分工 | 各成員負責什麼；常駐成員與按任務參與的顧問分別如何參與 |
| 共享上下文 | 哪些資料可交給哪些成員，採用哪個版本，不預設共享全部工作階段或私人記憶 |
| 協作交接 | 誰把哪個固定成果交給誰，怎樣映射輸入，接收方如何確認或拒收 |
| 工作安排 | 誰承擔輸入分發與輸出彙整；由宿主編排還是明確交辦的協調者處理 |
| 資源約束 | 每項工作的授權、應用、預算及停止條件；無進展時向誰升級 |
| 成果驗收 | 檢查哪些輸出，由誰驗收哪個版本，是否要求獨立複核 |

協調者是可選用的角色，不要求所有團隊都採用主管制。成員名單、群組聊天和組織圖也不能代替這些工作約定。

組合本身也有工作介面。例如團隊的 `deliver` 接收 `evidence`，必須交付 `report`、`evidence` 和 `review`。協調者或宿主需要說明：輸入交給誰，三個輸出分別來自哪個固定成果，由誰檢查是否齊全。缺少這些對應關係時，團隊工作仍未就緒。

![Teloa AI 員工按 Team 契約協作，人負責審核與驗收](../diagrams/zh-CN/delivery.png)

*Teloa AI 員工按 Team 契約協作，人負責審核與驗收。*

圖中的範例流程分為六步：

1. **人類負責人明確交辦。** 給出目標、輸入與授權範圍，選擇團隊工作入口，確定交付和驗收要求。
2. **宿主或協調者驗證並分發。** 檢查契約、依賴和實例綁定，只分發獲准材料，並建立實際任務歸屬。
3. **分析 AI 員工提交成果。** 執行已交辦工作，固定報告與證據版本，記錄實際貢獻者。
4. **複核 AI 員工確認接收並複核。** 核對輸入，接收後完成檢查並固定複核意見；拒收時記錄原因，交回協調處理。
5. **宿主或協調者檢查成果齊全。** 按團隊契約彙整固定來源，檢查必需輸出，保留貢獻者和交接記錄。
6. **人類負責人驗收並決定採用。** 驗收指定成果版本，另行記錄是否用於業務；通過驗收不自動核准對外動作。

這裡採用「分析、複核、人工驗收」的範例分工；具體團隊按自己的契約安排。跨環節保持同一條證據鏈：**獲准輸入 → 固定報告 → 複核意見 → 最終成果包**。

成員間的一次交接可以寫成下面的契約片段，取自[完整組合範例](../examples/composition-fixture.json)：

```json
{
  "id": "review-report",
  "from": "member/analyst/inspect",
  "to": "member/quality/review",
  "when": "已有固定报告与证据且获得本项交接授权",
  "inputs": {
    "report": "report",
    "evidence": "evidence"
  }
}
```

`inputs` 左側是接收方欄位，右側是發送方輸出欄位。這段定義不發送訊息，也不執行派工。真正交接時，還要記錄發送人與接收人、來源 Run、成果版本、獲准傳遞的材料，以及接收或拒收結果。訊息發到了群組裡，不等於接收方已經拿到可用輸入。

圖中複核 AI 員工產出的是複核意見；完整成果包仍由指定負責人驗收。獨立驗收要檢查實際貢獻者。若複核人改寫了報告，新的報告也包含其貢獻，不能繼續把這個人視為該版本的獨立驗收者。

## 03 AI Org 在團隊之上補充什麼

組織可以組合多個團隊和工作者，並約定跨團隊的責任、資源限制與變更規則。增加人數或再建一層群組，不會自動形成這些約定。

**AI Org 的組成是：個體和團隊的組合＋跨團隊責任＋資源與資訊邊界＋升級與變更規則。**

| 組織要素 | 對已有團隊補充什麼 |
| --- | --- |
| 個體與團隊的組合 | 列明成員和固定定義版本；子團隊通過自己的工作介面參與，不自動暴露全部內部能力 |
| 跨團隊責任 | 明確對組織範圍負責的可信主體，以及跨團隊問題的升級去向 |
| 資源與資訊邊界 | 規定資料、預算和執行限制適用於哪些成員，由宿主核對和執行 |
| 升級與變更規則 | 規定成員任職與撤任、定義變更、暫停恢復，以及進行中的工作的處理方式 |

![以 Teloa AI 員工為例，說明 Worker、AI Team 與 AI Org 的組合](../diagrams/zh-CN/composition.png)

*以 Teloa AI 員工為例，說明 Worker、AI Team 與 AI Org 的組合。*

例如，一個資安營運組織可以由研判調查團隊和偵測工程團隊組成，共用一名品質檢查 AI 員工。共用需要綁定同一個實際實例，不能只因為兩個位置引用同一職務範本就推斷是同一個員工。

組織還要說明誰對組織範圍負責，誰決定成員任職或撤任，員工暫停以後進行中的工作怎樣處理，以及哪些資料和預算限制適用於哪些成員。同一個員工參與兩支團隊，不代表兩邊歷史可以互讀，也不產生兩份原本只有一份的預算。

這是一種可表達的組織結構。是否已在某個產品執行，需要該產品提供綁定、授權和執行證據。圖中場景與下載的結構夾具不同：夾具的 A、B 兩組同時重用分析和品質檢查員工，用於說明實例綁定，未設定真實偵測工程職務。

## 04 技術上分清定義、實例和一次執行

Worker 定義像 AI 員工的職務說明和工作契約；Worker 實例對應 Teloa 中一位具體的 AI 員工；Run 是這個員工的一次執行。職務範本升級，舊 Run 仍保留原版本。更換模型，也不必把員工歷史變成另一個人的歷史。

![以 Teloa 為例：Worker 定義、AI 員工實例、Run 與成果驗收](../diagrams/zh-CN/architecture.png)

*以 Teloa 為例：Worker 定義、AI 員工實例、Run 與成果驗收。*

**技術鏈路是：標準定義 → 契約驗證 → 宿主綁定 → 一次 Run → 固定成果 → 驗收記錄 → 業務採用。** 各環節分別回答不同問題：

| 層次 | 物件或環節 | 記錄和檢查的內容 |
| --- | --- | --- |
| 標準定義 | 核心定義與工作擴展 | `id`、`revision`、`kind` 與成員固定引用；職責、工作輸入輸出、依賴、協作和驗收要求 |
| 宿主設定 | 契約與能力驗證 | 引用是否存在、輸入輸出契約是否完整、必要能力是否受支援；缺項時將受影響工作標為未就緒 |
| 宿主設定 | Worker 實例與綁定 | 具體 AI 員工的持續身分，以及本項工作的資料、模型、應用連線和有效授權 |
| 實際執行 | Work、任務與 Run | Work 是可重複呼叫的工作契約；任務是一次具體交辦；Run 記錄一次執行的輸入、定義版本和實際執行主體 |
| 工作交付 | 固定成果 | 可查看的成果內容、版本、證據和實際貢獻者，而不只是「執行結束」狀態 |
| 工作交付 | 驗收記錄 | 誰依據哪些要求檢查了哪個成果版本，以及檢查結論；要求獨立時還需核對實際貢獻者 |
| 業務決定 | 採用記錄 | 負責人是否決定使用該成果；採用與驗收分別記錄，不自動授予發佈或處置權限 |

例如，「材料摘要職務第 2 修訂」是一份定義；按它建立的「資料整理員」是一位實例；本週摘要和下週摘要是兩項任務，各自保留 Run 與成果。更新職務範本不回寫舊 Run，也不把舊成果署名轉給新員工。

核心格式只保留 `agent` 與 `organization`。Worker 使用 `agent` 加必需工作擴展，Team 使用 `organization` 加協作契約，Org 再增加治理契約。這樣可以沿同一套引用和版本規則組合，無需為每種產品稱呼另造檔案類型。

宿主是實際執行這些定義的平台，例如 Teloa。它負責把定義綁定到真實實例、資料、工具連線、模型與授權主體，檢查輸入和依賴，並記錄執行和成果。匯入檔案只帶來一份待解釋的定義，不會自動連線帳號、授予權限、啟動執行或啟用例行。結構驗證、設定就緒、執行成功、成果驗收和業務採用需要各自的證據，不能互相代替。

## 05 一個可以逐欄位核對的例子

[材料摘要 Worker](../examples/document-worker.json)是一份完整 JSON 定義，包含全部必需欄位。它的 `summarize` 接受一個非空 `material` 字串，輸出非空 `summary` 和字串陣列 `openQuestions`。以下輸入輸出是手寫的教學範例：

```json
{
  "material": "示例周报：甲项目本周完成三份资料摘要。第二份缺少来源日期，负责人要求补充。材料没有提供工时或客户反馈。"
}
```

```json
{
  "summary": "甲项目本周完成三份资料摘要，其中第二份仍需补充来源日期。",
  "openQuestions": [
    "第二份资料的来源日期是什么？",
    "现有材料未提供工时或客户反馈，无法据此评价效率或满意度。"
  ]
}
```

結構檢查能發現缺欄位和錯誤類型。負責人還要檢查內容：是否忠於材料，是否把沒有工時資料的情況寫成「效率提升」。驗收針對固定輸出版本；修改以後，需要按約定重新檢查。

換成 SOC 研判，仍可重用這種關係。假設教學材料只包含一條 WAF 的 HTTP 403 記錄，那麼報告只能解釋這條記錄支持什麼結論，並註明缺少後端和終端證據。它不能據此斷言伺服器已經失陷，也不能斷言完全安全。更深調查需要哪些資料，寫成明確缺口；封禁、隔離等處置需要相應工具與授權。這一例子沒有連線真實環境或執行攻擊。

## 06 Grok Bot 與 Teloa 怎樣對應

Teloa 的 AI 員工是 AI Worker 在產品中的具體表達，Grok Bot 也可以按 AI Worker 來描述。AI 員工、Bot 是各產品使用的概念；AI Worker 提供共同的技術定義，適配時再逐項核對職責、工作契約與宿主行為。Grok 的公開設計介紹了可持續存在的 Bot，以及 Skills、Routines 等組成；這可支持概念上的比較，不等於已有轉換器或官方相容認證。[Grok 設計說明](https://x.ai/news/designing-grok-bot)

| 產品概念 | 在本規範中的對應 | 適配時需要確認 |
| --- | --- | --- |
| Teloa AI 員工；Grok Bot | Worker 定義與實際實例 | 持續身分、職責、工作 I/O 和驗收是否完整 |
| 職務提示詞、Bot profile | `instructions` 與 `responsibility` | 工作邊界是否具體，缺項不得從名字推斷 |
| Skills、知識、SOP | 按用途引用的 `resources` | 真實版本、來源與工作依賴 |
| 工具或外掛 | 能力引用、應用資源與宿主連線 | 實際授權，憑據留在宿主 |
| Teloa 群組與專案 | 團隊溝通和上下文載體 | 還需明確分工、交接和團隊成果契約 |
| Grok Team Bot | 共享 Worker | 使用者的授權、私人工作階段與私人例行分別保留 |

Grok Team Bot 的文件描述的是多人使用同一個 Bot。它與「多個 Worker 分工完成一份成果」的 AI Team 不同。適配共享 Worker 時，個人例行保留在宿主的私人安排中，不進入共享定義；只有作者明確發佈並移除私有內容的範本才能被分享，匯入後仍不自動啟用。[Team Bots](https://docs.x.ai/grok-bot/team-bots)

更細的 Teloa 欄位對應與適配缺項見[映射文件](mappings.md)。

## 07 重用現有規範，保持範圍清楚

OASF 提供 Agent 的發現記錄、領域與能力分類，適合幫助使用者找到候選能力。本規範保留這些原生分類及其版本，另用工作契約說明輸入、輸出與驗收。OASF 的分類技能和可執行 Skill 套件不是同一種物件。[OASF Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Oracle Agent Spec 的元件引用、輸入輸出與組合定義值得重用。本規範借鏡這些思路；適配具體版本時仍須逐項轉換介面、引用和執行語義，不能把欄位改名就稱為互通。[Oracle Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

JSON 用於交換固定定義，YAML 可以用於編寫。YAML 轉換須拒絕重複鍵、錨點、別名、顯式標籤、非有限數值和多文件等不在約定內的輸入，並保留數值與字串含義。例如 `revision: "1"` 是字串，`revision: 1` 會因類型錯誤被拒絕。兩種檔案不能成為同一修訂下各自隨意修改的來源。

## 08 怎樣開始採用

選一項已有工作，先寫清輸入、輸出、依賴、負責位置和驗收。用真實實例執行後，檢查接收方實際取得的材料與固定成果，再擴大到團隊。如果當前平台無法兌現某項關鍵約束，就把相應工作標為未就緒。

本版希望先把這些關係定義清楚。要成為可由產業共同採用的規範，還需要獨立實現的互通證據、非 SOC 場景，以及公開的變更討論。儲存庫採用 Apache-2.0 授權，歡迎從一個具體歧義或反例開始參與。[標準儲存庫](https://github.com/teloa-ai/ai-worker-standard) · [回饋入口](https://github.com/teloa-ai/ai-worker-standard/issues)
