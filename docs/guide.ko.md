# AI Worker: 직원 한 명이 일하고 팀이 결과물을 제공하는 방식

[Languages / 语言](languages.md)

**Max Luo, Morgan Chen｜Teloa 공동 창업자** · 2026년 10월 18일

> 번역 안내: [중국어 간체판](guide.zh-CN.md)이 기준 원문입니다. 이 문서는 한국어 번역본이며, 한국어가 모국어인 업계 전문가의 전면 검토는 아직 거치지 않았습니다. 차이를 발견하면 알려 주시기 바랍니다. 동일한 예제를 비교할 수 있도록 JSON／YAML 예제의 값은 원문 그대로 유지합니다. 그림의 표기는 영어이며 주요 관계는 모두 한국어 본문으로 설명합니다.

Teloa에서는 사용자가 만들고 함께 일하는 작업 주체를 **AI 직원**이라고 부릅니다. **AI Worker는 그 바탕이 되는 범용 표준 개념입니다.** 지속적인 정체성, 책임, 작업 계약 및 협업 경계로 AI 직원의 일하는 방식을 설명합니다. 제품의 AI 직원과 소속 AI 팀 모두 이 표준으로 구성과 납품 요구를 설명할 수 있습니다.

AI 직원에게 이름을 주고 역할 프롬프트를 작성하면 시험 사용을 시작할 수 있습니다. 그러나 두 번째 일을 맡길 때는 질문이 구체적이 됩니다. 지난번과 같은 직원인가? 이번에는 어떤 자료를 사용했는가? 다음 구성원에게 무엇을 전달했는가? 보고서 검토 후 누가 채택을 결정하는가?

AI Worker 표준은 이런 약속을 명확히 하여 사용자가 AI 직원이 맡은 책임과 제공한 결과물을 확인하게 하고, 서로 다른 제품에 공통 기술 표현을 제공합니다.

이 문서는 코어 명세와 작업 및 협업 프로파일을 포함한 **AI Worker 표준 1.0**을 소개합니다. 예제는 학습 자료이며 고객 사례나 실행 증거가 아닙니다. [명세 본문](../spec/core.ko.md)이 기술 요구를 규정합니다.

세 핵심 개념은 다음처럼 구분할 수 있습니다.

| 개념 | 정의 | 답하는 질문 |
| --- | --- | --- |
| **AI Worker** | 지속적 정체성을 갖고 명시적 권한 범위 안에서 책임을 맡아 작업을 수락하며 검수 가능한 결과를 제공하는 AI 작업 주체 | 이 AI 직원은 누구이며, 무엇을 맡고, 어떻게 완료를 증명하는가? |
| **AI Team** | 공동 결과물을 중심으로 구성원 분담·자료 인계·검수 요구를 명확히 한 협업 구성 | 여러 AI 직원이 한 작업을 어떻게 함께 완료하는가? |
| **AI Organization(AI Org)** | 개별 주체와 팀의 구성에 조직 책임·자원 및 정보 경계·변경 거버넌스를 추가한 조직 | 여러 팀을 누가 책임지고 자원을 배분하며 변경을 관리하는가? |

'지속적 정체성'은 작업이 바뀌어도 같은 작업자를 식별할 수 있다는 뜻이며 상시 접속·전용 기계·장기 기억을 요구하지 않습니다. '책임'은 작업 귀속과 추적 가능성을 뜻하고 AI에 법인격을 부여하지 않습니다. 아래 본문·표·단계에서 이 관계를 설명하며 그림은 같은 내용의 시각적 개요를 제공합니다.

## 01 AI 직원이 명확히 해야 하는 것

자료 요약 담당 AI 직원을 예로 들겠습니다. 이 직원은 주어진 자료로 요약을 작성하고 자료가 제공하지 않은 사실은 질문으로 남깁니다. 같은 역할을 반복 수행하면서 구체적 작업마다 다른 모델을 사용할 수도 있습니다. 각 결과는 여전히 같은 AI 직원에 귀속됩니다. 기술적으로는 특정 Worker 인스턴스에 대응하며 사용한 정의 버전을 기록합니다.

![Teloa AI 직원, Grok Bot, AI Worker의 개념 대응과 다섯 구성 그룹](../diagrams/en/worker.png)

*Teloa AI 직원, Grok Bot, AI Worker의 개념 대응과 다섯 구성 그룹.*

그림의 화살표는 개념 대응을 뜻합니다. Teloa는 AI 직원이라는 제품 개념을 유지하고 Grok은 Bot을 유지합니다. 둘을 AI Worker의 공통 정의로 설명할 수 있지만 그림 자체가 적용 완료나 공급업체 인증을 의미하지는 않습니다.

**AI 직원의 다섯 구성 그룹**은 역할에 관해 무엇을 정해야 하는지 설명합니다. 자원은 실제 작업에 따라 선택하며 모든 직원에게 모든 도구를 갖추도록 요구하지 않습니다.

| 구성 | 일반적 의미 | 자료 요약 AI 직원의 구체적 설정 |
| --- | --- | --- |
| **역할과 책임** | 지속적 정체성·역할 임무·책임 경계·자율 판단·확인·에스컬레이션 규칙 | 주어진 자료를 요약하고 모순을 나열하며 작성자를 대신해 사실을 만들지 않음 |
| **방법과 근거** | Skill은 수행 방법, 지식은 판단 자료, SOP는 단계·확인 지점·예외 처리를 제공. 출처와 버전을 각각 유지 | 이번 입력 자료를 사용하고 복잡한 작업에서 Skill·지식·SOP 추가 |
| **작업과 일정** | 작업 계약은 목표·입력·출력·의존성·책임 위치·검수를 정하고, 정기 작업은 언제 어느 작업을 호출할지 정함 | `summarize` 작업 진입점을 제공하고 요청받으면 실행. 정기 일정은 설정하지 않음 |
| **실행 조건** | 애플리케이션·도구·자료 범위·유효 권한·모델·예산·실행 공간 등의 조건 | 허용된 자료만 읽고 외부 게시에는 별도 확인 필요 |
| **경험과 결과물** | 기억 규칙은 경험 저장·사용·철회를 정함. 결과물과 증거는 버전을 고정하고 요구에 따라 검수 | 요약과 미해결 질문을 출력하고 책임자가 원문 일치 여부 확인 |

기억 저장소, 앱 연결, 정기 일정은 필수 설정이 아닙니다. 자원이 필요한지는 약속한 작업에 달려 있습니다. 외부 자료를 조회하려면 연결과 권한을 조건으로 명시해야 합니다. 입력 텍스트만 요약한다면 모듈 목록을 채우려고 도구를 추가할 필요는 없습니다.

완전한 Worker 정의에는 최소한 정체성과 리비전, 책임과 판단 경계, 그리고 입력·출력·책임 위치·검수 요구를 설명한 작업 하나가 필요합니다. 실제 사용에는 호스트가 구체적인 인스턴스·실행 조건·신뢰된 권한을 바인딩하는 과정도 필요합니다. 다섯 그룹은 읽기 위한 구성으로 정체성·책임·Skills·지식·SOP·작업 템플릿·정기 작업·애플리케이션·권한·실행 조건·경험·결과물과 품질을 포괄합니다. 구체적 필드는 [작업 및 협업 프로파일](../spec/work-profile.ko.md)을 참조하십시오.

## 02 팀 납품은 모든 인계를 추적할 수 있어야 한다

AI에게 '자료를 정리하고 결론을 검토하는 일'을 맡긴다고 가정해 보겠습니다. 분석 AI 직원이 자료를 읽고 검토 AI 직원이 증거를 확인하며 팀이 보고서와 검토 의견을 제공합니다. 그룹 채팅은 의사소통을 쉽게 하지만 팀 계약은 공동 결과물·구성원 분담·인계 조건·중단 규칙도 명확히 해야 합니다.

**AI Team의 구성은 공동 목표＋구성원과 역할 분담＋공유 맥락 경계＋협업 인계＋작업 일정＋자원 제약＋결과물 검수입니다.**

| 팀 요소 | 명확히 해야 할 약속 |
| --- | --- |
| 공동 목표 | 팀이 외부에서 받는 작업과 최종 제공 결과물 |
| 구성원과 역할 분담 | 각 구성원 책임, 상시 구성원과 작업별 자문역의 참여 방식 |
| 공유 맥락 | 어떤 자료와 버전을 어떤 구성원에게 전달할 수 있는지. 전체 대화나 개인 기억을 기본 공유하지 않음 |
| 협업 인계 | 누가 어떤 고정 결과물을 누구에게 전달하고, 입력을 어떻게 매핑하며 수신자가 어떻게 확인하거나 거부하는지 |
| 작업 일정 | 입력 분배와 출력 취합의 담당. 호스트 오케스트레이션인지 명시적으로 배정한 조정자인지 |
| 자원 제약 | 작업별 권한·앱·예산·중단 조건, 진전이 없을 때 보고할 대상 |
| 결과물 검수 | 어떤 출력을 누가 어느 버전으로 검수하며 독립 검토가 필요한지 |

조정자는 선택적 역할이며 모든 팀에 관리자 체계를 요구하지 않습니다. 구성원 목록·그룹 채팅·조직도도 이런 작업 약속을 대체할 수 없습니다.

구성 자체에도 작업 인터페이스가 있습니다. 예를 들어 팀의 `deliver`는 `evidence`를 받아 `report`, `evidence`, `review`를 반드시 제공합니다. 조정자 또는 호스트는 입력을 누가 받고 세 출력은 각각 어떤 고정 결과물에서 나오며 누가 완전성을 확인하는지 설명해야 합니다. 이 대응이 없으면 팀 작업은 아직 준비되지 않은 상태입니다.

![Teloa AI 직원이 Team 계약으로 협업하고 사람이 승인과 검수를 담당](../diagrams/en/delivery.png)

*Teloa AI 직원은 Team 계약으로 협업하고 사람은 승인과 검수를 담당합니다.*

그림의 예제 절차는 여섯 단계입니다.

1. **사람 책임자가 명확히 작업을 배정합니다.** 목표·입력·권한 범위를 제시하고 팀 작업 진입점을 선택하며 납품·검수 요구를 정합니다.
2. **호스트 또는 조정자가 검증하고 분배합니다.** 계약·의존성·인스턴스 바인딩을 확인하고 허용된 자료만 배포하며 실제 작업 귀속을 확립합니다.
3. **분석 AI 직원이 결과물을 제출합니다.** 배정된 작업을 수행하고 보고서와 증거 버전을 고정하며 실제 기여자를 기록합니다.
4. **검토 AI 직원이 수신을 확인하고 검토합니다.** 입력을 확인하여 받은 뒤 검사를 완료하고 검토 의견을 고정합니다. 거부하면 사유를 기록하고 조정을 위해 돌려보냅니다.
5. **호스트 또는 조정자가 결과물 완전성을 확인합니다.** 팀 계약에 따라 고정 출처를 취합하고 필수 출력을 확인하며 기여자와 인계 기록을 보관합니다.
6. **사람 책임자가 검수하고 채택을 결정합니다.** 지정 결과물 버전을 검수하고 업무 사용 여부를 별도로 기록합니다. 검수 통과가 외부 동작을 자동 승인하지는 않습니다.

이는 '분석·검토·사람의 검수'라는 역할 분담 예제이며, 구체적인 팀은 자체 계약에 따릅니다. 단계 사이에는 같은 증거 연결을 유지합니다. **허용된 입력 → 고정 보고서 → 검토 의견 → 최종 결과물 패키지**입니다.

구성원 간 한 번의 인계는 [완전한 구성 예제](../examples/composition-fixture.json)의 다음 계약 조각으로 표현할 수 있습니다.

```json
{
  "id": "review-report",
  "from": "member/analyst/inspect",
  "to": "member/quality/review",
  "when": "已有固定报告与证据且获得本项交接授权",
  "inputs": {
    "report": "report",
    "evidence": "evidence"
  }
}
```

`inputs`의 왼쪽은 수신 측 필드이고 오른쪽은 송신 측 출력 필드입니다. 중국어 조건은 '고정된 보고서와 증거가 있고 이번 인계 권한을 받았음'을 요구합니다. 이 정의 자체가 메시지를 보내거나 작업을 배정하지는 않습니다. 실제 인계 때는 송신자·수신자·출처 Run·결과물 버전·전달을 허가받은 자료·수신 또는 거부 결과도 기록해야 합니다. 그룹에 메시지를 보냈다고 수신 측이 사용 가능한 입력을 확보한 것은 아닙니다.

그림에서 검토 AI 직원이 만드는 것은 검토 의견입니다. 완전한 결과물 패키지는 지정 책임자가 검수합니다. 독립 검수는 실제 기여자를 확인해야 합니다. 검토자가 보고서를 고쳤다면 새 보고서에는 그 사람의 기여도 포함되므로, 그 버전의 독립 검수자로 계속 볼 수 없습니다.

## 03 AI Org가 팀에 추가하는 것

조직은 여러 팀과 Worker를 구성하고 팀 간 책임·자원 제한·변경 규칙을 정할 수 있습니다. 인원수를 늘리거나 그룹 계층을 하나 더 만든다고 이런 약속이 자동으로 생기지는 않습니다.

**AI Org의 구성은 개별 주체와 팀의 구성＋팀 간 책임＋자원 및 정보 경계＋에스컬레이션과 변경 규칙입니다.**

| 조직 요소 | 기존 팀에 추가하는 내용 |
| --- | --- |
| 개별 주체와 팀의 구성 | 구성원과 고정 정의 버전을 나열. 하위 팀은 자체 작업 인터페이스로 참여하며 모든 내부 능력을 자동 노출하지 않음 |
| 팀 간 책임 | 조직 범위를 책임지는 신뢰 주체와 팀 간 문제의 에스컬레이션 대상을 명시 |
| 자원 및 정보 경계 | 데이터·예산·실행 제한이 어느 구성원에게 적용되는지 정하고 호스트가 확인·집행 |
| 에스컬레이션과 변경 규칙 | 구성원 임명·해임, 정의 변경, 일시 중지·재개, 진행 중 작업 처리 규정 |

예를 들어 보안 운영 조직은 분석 조사 팀과 탐지 엔지니어링 팀으로 구성되고 한 명의 품질 검토 AI 직원을 공유할 수 있습니다. 공유하려면 같은 실제 인스턴스에 바인딩해야 합니다. 두 자리가 같은 역할 템플릿을 참조한다는 이유만으로 같은 직원이라고 추론해서는 안 됩니다.

조직은 조직 범위의 책임자, 구성원 임명·해임 결정자, 직원 일시 중지 후 진행 중 작업 처리, 자료와 예산 제한의 적용 대상도 명시해야 합니다. 한 직원이 두 팀에 참여한다고 양쪽 기록을 서로 읽을 수 있는 것은 아니며 원래 하나뿐인 예산이 두 개로 늘어나지도 않습니다.

이는 표현할 수 있는 조직 구조입니다. 실제 제품에서 운영되는지는 그 제품의 바인딩·권한·실행 증거가 있어야 알 수 있습니다. 그림의 상황은 다운로드하는 구조 픽스처와 다릅니다. 픽스처의 A·B 팀은 분석 직원과 품질 검토 직원을 모두 재사용하여 인스턴스 바인딩을 설명하며 실제 탐지 엔지니어링 역할은 설정하지 않습니다.

## 04 기술적으로 정의, 인스턴스, 한 번의 실행 구분하기

Worker 정의는 AI 직원의 역할 설명과 작업 계약에 해당합니다. Worker 인스턴스는 Teloa의 특정 AI 직원이고, Run은 그 직원의 한 번의 실행입니다. 역할 템플릿을 업그레이드해도 기존 Run은 원래 버전을 유지합니다. 모델을 바꾼다고 직원 기록을 다른 주체의 기록으로 옮길 필요도 없습니다.

![Teloa 예제: Worker 정의, AI 직원 인스턴스, Run 및 결과물 검수](../diagrams/en/architecture.png)

*Teloa 예제: Worker 정의, AI 직원 인스턴스, Run 및 결과물 검수.*

**기술 경로는 표준 정의 → 계약 검증 → 호스트 바인딩 → 한 번의 Run → 고정 결과물 → 검수 기록 → 업무 채택입니다.** 각 단계는 다른 질문에 답합니다.

| 계층 | 객체 또는 단계 | 기록하고 확인하는 내용 |
| --- | --- | --- |
| 표준 정의 | 코어 정의와 작업 확장 | `id`·`revision`·`kind`·구성원 고정 참조, 책임·작업 입력과 출력·의존성·협업·검수 요구 |
| 호스트 설정 | 계약 및 능력 검증 | 참조 존재, 입출력 계약 완전성, 필수 능력 지원. 부족하면 해당 작업을 미준비로 표시 |
| 호스트 설정 | Worker 인스턴스와 바인딩 | 특정 AI 직원의 지속 정체성과 이번 작업의 자료·모델·앱 연결·유효 권한 |
| 실제 실행 | Work, 작업, Run | Work는 반복 호출하는 작업 계약, 작업은 구체적인 배정, Run은 한 번의 실행 입력·정의 버전·실제 실행 주체 기록 |
| 작업 납품 | 고정 결과물 | 확인 가능한 결과물 내용·버전·증거·실제 기여자. 단순히 '실행 종료' 상태만으로는 부족 |
| 작업 납품 | 검수 기록 | 누가 어떤 기준으로 어느 결과물 버전을 검사했고 어떤 결론을 냈는지. 독립 검수가 필요하면 실제 기여자도 확인 |
| 업무 결정 | 채택 기록 | 책임자가 결과물을 사용할지 결정. 채택과 검수는 별도 기록이며 게시나 차단·격리 권한을 자동 부여하지 않음 |

예를 들어 '자료 요약 역할 리비전 2'는 정의이고, 이를 바탕으로 만든 '자료 정리 담당자'는 인스턴스입니다. 이번 주 요약과 다음 주 요약은 두 작업이며 각각 Run과 결과물을 유지합니다. 역할 템플릿을 갱신해도 기존 Run을 다시 쓰거나 과거 결과물의 귀속을 새 직원에게 넘기지 않습니다.

코어 형식은 `agent`와 `organization`만 유지합니다. Worker는 `agent`와 필수 작업 확장을 사용하고 Team은 `organization`과 협업 계약을 사용하며 Org는 거버넌스 계약을 추가합니다. 같은 참조·버전 규칙으로 구성할 수 있어 제품 명칭마다 파일 유형을 새로 만들 필요가 없습니다.

호스트는 Teloa처럼 정의를 실제로 실행하는 플랫폼입니다. 정의를 실제 인스턴스·자료·도구 연결·모델·권한 주체에 바인딩하고 입력과 의존성을 검사하며 실행과 결과물을 기록합니다. 파일 가져오기는 해석할 정의를 확보할 뿐 계정 연결·권한 부여·실행 시작·정기 작업 활성화를 자동 수행하지 않습니다. 구조 검증·설정 준비 완료·실행 성공·결과물 검수·업무 채택은 각각 증거가 필요하며 서로 대체할 수 없습니다.

## 05 필드별로 확인할 수 있는 예제

[자료 요약 Worker](../examples/document-worker.json)는 모든 필수 필드를 포함한 완전한 JSON 정의입니다. `summarize`는 비어 있지 않은 `material` 문자열을 받아 비어 있지 않은 `summary`와 문자열 배열 `openQuestions`를 출력합니다. 아래 입력과 출력은 직접 작성한 학습용 예제입니다.

```json
{
  "material": "示例周报：甲项目本周完成三份资料摘要。第二份缺少来源日期，负责人要求补充。材料没有提供工时或客户反馈。"
}
```

```json
{
  "summary": "甲项目本周完成三份资料摘要，其中第二份仍需补充来源日期。",
  "openQuestions": [
    "第二份资料的来源日期是什么？",
    "现有材料未提供工时或客户反馈，无法据此评价效率或满意度。"
  ]
}
```

입력은 '프로젝트 A가 이번 주 자료 요약 세 건을 완료했고, 두 번째 자료의 출처 날짜가 없어 책임자가 보완을 요구했으며, 작업 시간이나 고객 피드백은 제공되지 않았다'는 주간 보고입니다. 출력 요약은 이 사실만 정리합니다. 미해결 질문에는 두 번째 자료의 출처 날짜와, 작업 시간·고객 피드백이 없어 효율이나 만족도를 평가할 수 없다는 점을 남깁니다.

구조 검사는 필드 누락과 잘못된 타입을 찾을 수 있습니다. 책임자는 내용도 확인해야 합니다. 원자료에 충실한지, 작업 시간 데이터도 없는데 '효율 향상'이라고 썼는지 확인합니다. 검수는 고정된 출력 버전에 적용하며 수정 후에는 합의된 검사를 다시 받아야 합니다.

SOC 분석에도 같은 관계를 재사용할 수 있습니다. 학습 자료에 WAF의 HTTP 403 기록 한 건만 있다면 보고서는 그 기록이 지지하는 결론을 설명하고 백엔드·엔드포인트 증거가 부족함을 명시해야 합니다. 이것만으로 서버 침해나 완전한 안전을 단정할 수 없습니다. 심층 조사에 필요한 데이터는 명확한 부족 항목으로 제시하고, 차단·격리 같은 대응에는 해당 도구와 권한이 필요합니다. 이 예제는 실제 환경에 연결하지 않았으며 공격도 실행하지 않았습니다.

## 06 Grok Bot과 Teloa의 대응

Teloa의 AI 직원은 AI Worker의 제품상 표현이며 Grok Bot도 AI Worker로 기술할 수 있습니다. AI 직원과 Bot은 각 제품 개념을 유지합니다. AI Worker는 공통 기술 정의를 제공하며, 적용 시 책임·작업 계약·호스트 동작을 항목별로 확인합니다. Grok의 공개 설계는 지속적으로 존재하는 Bot과 Skills·Routines 등의 구성을 설명합니다. 이는 개념 비교를 뒷받침하지만 변환기나 공식 호환성 인증의 존재를 뜻하지 않습니다. [Grok 설계 설명](https://x.ai/news/designing-grok-bot)

| 제품 개념 | 이 명세의 대응 | 적용 시 확인할 사항 |
| --- | --- | --- |
| Teloa AI 직원, Grok Bot | Worker 정의와 실제 인스턴스 | 지속 정체성·책임·작업 I/O·검수의 완전성 |
| 역할 프롬프트, Bot profile | `instructions`와 `responsibility` | 구체적 작업 경계. 없는 계약을 이름에서 추론하지 않음 |
| Skills, 지식, SOP | 용도별로 참조하는 `resources` | 실제 버전·출처·작업 의존성 |
| 도구 또는 플러그인 | 능력 참조·앱 자원·호스트 연결 | 실제 권한. 자격 증명은 호스트에 유지 |
| Teloa 그룹 및 프로젝트 | 팀 의사소통과 맥락 컨테이너 | 명확한 분담·인계·팀 결과물 계약이 여전히 필요 |
| Grok Team Bot | 공유 Worker | 사용자별 권한·개인 대화·개인 정기 작업을 각각 유지 |

Grok Team Bot 문서는 여러 사람이 같은 Bot 하나를 사용하는 형태를 설명합니다. 여러 Worker가 분담해 하나의 결과물을 완성하는 AI Team과 다릅니다. 공유 Worker를 적용할 때 개인 정기 작업은 호스트의 비공개 일정에 남기고 공유 정의에 넣지 않습니다. 작성자가 명시적으로 공개하고 비공개 내용을 제거한 템플릿만 공유할 수 있으며 가져온 뒤에도 자동 활성화하지 않습니다. [Team Bots](https://docs.x.ai/grok-bot/team-bots)

더 자세한 Teloa 필드 대응과 미지원 항목은 [매핑 문서](mappings.md)를 참조하십시오.

## 07 기존 명세를 재사용하되 범위를 명확히 유지하기

OASF는 Agent 탐색 레코드·분야·능력 분류를 제공하여 사용자가 후보 능력을 찾도록 돕습니다. 이 명세는 네이티브 분류와 버전을 유지하고, 별도의 작업 계약으로 입력·출력·검수를 설명합니다. OASF의 분류 스킬과 실행 가능한 Skill 패키지는 같은 종류의 객체가 아닙니다. [OASF Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Oracle Agent Spec의 컴포넌트 참조·입출력·구성 정의는 재사용할 가치가 있는 설계입니다. 이 명세는 그 개념을 참고합니다. 구체적인 버전에 적용할 때는 인터페이스·참조·실행 의미를 각각 변환해야 하며, 필드 이름만 바꿔 상호운용이라고 해서는 안 됩니다. [Oracle Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

JSON은 고정 정의 교환에 사용하며 YAML은 작성에 사용할 수 있습니다. YAML 변환은 중복 키·앵커·별칭·명시적 태그·비유한 수치·다중 문서 등 규약 밖 입력을 거부하고 숫자와 문자열의 의미를 보존해야 합니다. 예를 들어 `revision: "1"`은 문자열이지만 `revision: 1`은 타입 오류로 거부됩니다. 두 파일을 동일 리비전에서 각자 마음대로 수정하는 별도 원본으로 삼아서는 안 됩니다.

## 08 도입을 시작하는 방법

기존 작업 하나를 골라 입력·출력·의존성·책임 위치·검수를 먼저 명확히 합니다. 실제 인스턴스로 실행한 뒤 수신자가 실제로 얻은 자료와 고정 결과물을 확인하고 팀으로 확대합니다. 현재 플랫폼이 핵심 제약을 이행하지 못하면 해당 작업을 미준비로 표시합니다.

이번 판은 우선 이 관계를 명확히 정의하고자 합니다. 업계가 함께 채택할 수 있는 명세가 되려면 독립 구현의 상호운용 증거·비 SOC 시나리오·공개 변경 논의가 필요합니다. 저장소는 Apache-2.0 라이선스를 사용합니다. 구체적인 모호함이나 반례에서부터 참여해 주시기 바랍니다. [표준 저장소](https://github.com/teloa-ai/ai-worker-standard) · [피드백](https://github.com/teloa-ai/ai-worker-standard/issues)
