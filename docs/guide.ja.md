# AI Worker：一人の従業員が働き、チームが成果を届ける仕組み

[Languages / 语言](languages.md)

**Max Luo、Morgan Chen｜Teloa 共同創業者** · 2026 年 10 月 18 日

> 翻訳について：[簡体字中国語版](guide.zh-CN.md)が正本です。本書は日本語訳であり、日本語を母語とする業界専門家による全面的なレビューは未実施です。相違点を見つけた場合は報告をお願いします。同一の例を比較できるよう、JSON／YAML の例の値は原文のまま保持しています。図中の文字は英語ですが、すべての主要な関係を本文で日本語で説明しています。

Teloa では、利用者が作成して協業する作業主体を **AI 従業員**と呼びます。**AI Worker は、その背後にある汎用的な標準概念です。** 持続的なアイデンティティ、責務、作業契約、協業の境界によって、AI 従業員がどう働くかを表します。製品の AI 従業員と、それが属する AI チームの構成や納品要件を、この標準で説明できます。

AI 従業員に名前を付け、役割のプロンプトを書くだけでも試用は始められます。しかし二回目の仕事を依頼すると、問いは具体的になります。前回と同じ従業員なのか。今回はどの資料を使ったのか。次のメンバーに何を渡したのか。報告書をレビューした後、誰が採用を決めるのか。

AI Worker 標準はこれらの合意を明確にし、利用者が AI 従業員の責任範囲と納品内容を確認できるようにします。同時に、異なる製品で共通に使える技術的な表現を提供します。

本書は、コア仕様と作業・協業プロファイルを含む **AI Worker 標準 1.0** を紹介します。例は学習用の素材であり、顧客事例や実行の証拠ではありません。[仕様本文](../spec/core.ja.md)が技術要件を定めます。

三つの主要概念は次のように区別できます。

| 概念 | 定義 | 答える問い |
| --- | --- | --- |
| **AI Worker** | 持続的なアイデンティティを持ち、明示された権限範囲で責務を担い、仕事を受け付け、検収可能な成果を届ける AI の作業主体 | この AI 従業員は誰で、何を担当し、どう完了を示すか |
| **AI Team** | 共通成果のためにメンバーの分担、資料の引き継ぎ、検収要件を明確にした協業構成 | 複数の AI 従業員が一つの仕事をどう完成させるか |
| **AI Organization（AI Org）** | 個体とチームの構成に、組織責任、リソース・情報の境界、変更ガバナンスを加えた組織 | 複数チームを誰が担い、リソース配分と変更をどう管理するか |

「持続的なアイデンティティ」とは、タスクをまたいで同じ働き手を識別できることです。常時オンライン、専用マシン、長期記憶は必須ではありません。「責任」は作業の帰属と追跡可能性を表し、AI に法的人格を与えません。以下では文章、表、手順で関係を説明し、図で同じ内容の全体像を示します。

## 01 AI 従業員が明確にすべきこと

資料要約を担当する AI 従業員を考えます。与えられた資料から要約を作り、資料にない事実は未解決の問いとして残します。同じ役割を繰り返し担当し、具体的なタスクごとに別のモデルを使うこともできます。各回の結果は同じ AI 従業員に帰属します。技術的には特定の Worker インスタンスに対応し、使用した定義バージョンを記録します。

![Teloa の AI 従業員、Grok Bot、AI Worker の概念対応と五つの構成グループ](../diagrams/en/worker.png)

*Teloa の AI 従業員、Grok Bot、AI Worker の概念対応と五つの構成グループ。*

図の矢印は概念の対応を表します。Teloa は AI 従業員という製品概念を保ち、Grok は Bot を保ちます。双方を AI Worker の共通定義で説明できますが、図だけで対応完了やベンダー認証を示すことはありません。

**AI 従業員の五つの構成グループ**は、役割について何を合意すべきかを整理します。リソースは実際の作業に応じて選び、全従業員に全ツールを揃えることは要求しません。

| 構成 | 一般的な意味 | 資料要約 AI 従業員の具体的設定 |
| --- | --- | --- |
| **役割と責務** | 持続的なアイデンティティ、使命、責務の境界、自律判断・確認・エスカレーションのルール | 与えられた資料を要約し、矛盾を列挙する。作成者に代わって事実を作らない |
| **方法と根拠** | Skill は方法、知識は判断材料、SOP は手順・確認点・例外対応を示す。出典とバージョンを別々に保持する | 今回の入力資料を使う。複雑な仕事では Skill、知識、SOP を追加する |
| **作業と予定** | 作業契約が目標・入力・出力・依存関係・責任位置・検収を定め、定例作業がどの作業をいつ呼ぶかを定める | `summarize` の入口を提供し、依頼されたときに実行する。定例作業は設けない |
| **実行条件** | アプリケーションとツール、資料範囲、有効な権限、モデル・予算・作業空間の要件 | 許可された資料だけを読み、外部公開は別途確認する |
| **経験と成果** | 記憶ルールが経験の保存・利用・撤回を定め、成果と証拠はバージョンを固定して要件に沿って検収する | 要約と未解決の問いを出力し、責任者が原文との一致を確認する |

記憶ストア、アプリケーション接続、定期スケジュールの設定は強制ではありません。リソースが必須かどうかは、約束した仕事で決まります。外部資料を調べるなら接続と権限を条件に含めなければなりません。入力テキストを要約するだけなら、項目を埋めるためにツールを追加する必要はありません。

完全な Worker 定義には、少なくともアイデンティティとリビジョン、責務と判断の境界、入力・出力・責任位置・検収要件を明示した一つの作業が必要です。実際の利用には、ホストが具体的なインスタンス、実行条件、信頼できる権限をバインドすることも必要です。五つのグループは読むための整理であり、アイデンティティ、責任、Skills、知識、SOP、作業テンプレート、定例作業、アプリケーション、権限、実行条件、経験、成果と品質を網羅します。フィールドの詳細は[作業・協業プロファイル](../spec/work-profile.ja.md)を参照してください。

## 02 チームの納品では一回ごとの引き継ぎを追跡する

AI に「資料を整理し結論を確認する」仕事を依頼するとします。分析担当の AI 従業員が資料を読み、レビュー担当の AI 従業員が証拠を確認し、チームが報告書とレビュー意見を納品します。グループチャットは交流を容易にしますが、チーム契約では共同成果、メンバーの分担、引き継ぎ条件、停止ルールも明確にする必要があります。

**AI Team の構成は、共通目標＋メンバーと役割分担＋共有コンテキストの境界＋協業上の引き継ぎ＋作業の予定＋リソース制約＋成果の検収です。**

| チーム要素 | 明確にすべき合意 |
| --- | --- |
| 共通目標 | チームが外部から受け付ける仕事と最終的な成果 |
| メンバーと役割分担 | 各メンバーの担当、常設メンバーとタスク単位のコンサルタントの参加方法 |
| 共有コンテキスト | どの資料のどのバージョンを誰に渡せるか。会話全体や私的記憶を既定で共有しない |
| 協業上の引き継ぎ | 誰がどの固定成果を誰に渡すか、入力の対応付け、受信側の確認または拒否 |
| 作業の予定 | 入力配布と出力集約の担当。ホストのオーケストレーションか、明示的に依頼したコーディネーターか |
| リソース制約 | 作業ごとの権限・アプリケーション・予算・停止条件、および進展がない場合の報告先 |
| 成果の検収 | どの出力のどのバージョンを誰が確認し、独立レビューを必要とするか |

コーディネーターは任意の役割であり、すべてのチームに管理者方式を要求しません。メンバー一覧、グループチャット、組織図も、これらの作業上の合意の代わりにはなりません。

構成自体にも作業インターフェースがあります。たとえばチームの `deliver` は `evidence` を受け、`report`、`evidence`、`review` を必ず納品します。コーディネーターまたはホストは、誰に入力を渡し、三つの出力をどの固定成果から得て、誰が不足の有無を確認するかを説明する必要があります。この対応がなければ、チームの仕事はまだ準備完了ではありません。

![Teloa の AI 従業員は Team 契約に沿って協業し、人が承認と検収を担う](../diagrams/en/delivery.png)

*Teloa の AI 従業員は Team 契約に沿って協業し、人が承認と検収を担います。*

図の例は六つの段階からなります。

1. **人の責任者が明示的に依頼する。** 目標、入力、権限範囲を示し、チームの作業入口を選び、納品と検収の要件を決めます。
2. **ホストまたはコーディネーターが検証して配布する。** 契約、依存関係、インスタンスのバインディングを確認し、許可された資料だけを配布して、実際のタスクの帰属を確立します。
3. **分析担当の AI 従業員が成果を提出する。** 割り当てられた仕事を実施し、報告書と証拠のバージョンを固定し、実際の貢献者を記録します。
4. **レビュー担当の AI 従業員が受信を確認しレビューする。** 入力を確認し、受信後に検査を終えてレビュー意見を固定します。拒否する場合は理由を記録して調整担当へ戻します。
5. **ホストまたはコーディネーターが成果の完全性を確認する。** チーム契約に従って固定された出典を集約し、必須出力を確認し、貢献者と引き継ぎの記録を保持します。
6. **人の責任者が検収し、採用を決める。** 指定バージョンの成果を検収し、業務で使うかどうかを別途記録します。検収合格は外部操作の自動承認ではありません。

これは「分析、レビュー、人による検収」という分担例です。実際のチームは自身の契約に従います。工程をまたいで、**許可された入力 → 固定報告書 → レビュー意見 → 最終成果パッケージ**という同じ証拠の連鎖を保ちます。

メンバー間の一回の引き継ぎは、[完全な構成例](../examples/composition-fixture.json)にある次の契約断片で表せます。

```json
{
  "id": "review-report",
  "from": "member/analyst/inspect",
  "to": "member/quality/review",
  "when": "已有固定报告与证据且获得本项交接授权",
  "inputs": {
    "report": "report",
    "evidence": "evidence"
  }
}
```

`inputs` の左側は受信側のフィールド、右側は送信側の出力フィールドです。中国語の条件は「固定された報告書と証拠があり、この引き継ぎの権限を得ている」ことを求めています。この定義だけでメッセージを送信したり作業を割り当てたりはしません。実際の引き継ぎでは、送信者と受信者、元の Run、成果バージョン、受け渡しを許可された資料、受信または拒否の結果を記録する必要があります。グループにメッセージを送ったことは、受信側が利用可能な入力を取得したことと同じではありません。

図でレビュー担当の AI 従業員が作るのはレビュー意見です。成果パッケージ全体は指定の責任者が検収します。独立した検収では実際の貢献者を確認する必要があります。レビュー担当者が報告書を書き換えた場合、その新バージョンには本人の貢献も含まれるため、同じバージョンの独立した検収者とは扱えません。

## 03 AI Org がチームに加えるもの

組織は複数のチームや Worker を構成し、チーム間の責任、リソース制限、変更ルールを合意できます。人数やグループ階層を増やすだけでは、これらの合意は生まれません。

**AI Org の構成は、個体とチームの構成＋チーム間の責任＋リソースと情報の境界＋エスカレーションと変更のルールです。**

| 組織要素 | 既存チームに追加するもの |
| --- | --- |
| 個体とチームの構成 | メンバーと固定定義バージョンを列挙する。サブチームは自身の作業インターフェースで参加し、全内部能力を自動公開しない |
| チーム間の責任 | 組織範囲の責任を持つ信頼主体と、チーム間の問題のエスカレーション先を明確にする |
| リソースと情報の境界 | データ・予算・実行の制限をどのメンバーへ適用するかを定め、ホストが確認・実施する |
| エスカレーションと変更ルール | メンバーの任命・解任、定義変更、停止・再開、進行中の作業の扱いを定める |

![Teloa の AI 従業員を例とした Worker、AI Team、AI Org の構成](../diagrams/en/composition.png)

*Teloa の AI 従業員を例とした Worker、AI Team、AI Org の構成。*

たとえばセキュリティ運用組織は、調査分析チームと検知エンジニアリングチームからなり、一人の品質確認 AI 従業員を共有できます。共有するには同じ実際のインスタンスへのバインディングが必要です。二つの位置が同じ役割テンプレートを参照しているだけでは、同じ従業員とは推定できません。

組織はさらに、組織範囲の責任者、メンバーの任命や解任を決める者、従業員の停止後に進行中の作業をどう扱うか、資料や予算の制限を誰に適用するかを定めます。同じ従業員が二つのチームに参加しても、双方の履歴が互いに読めるとは限らず、本来一枠しかない予算が二枠になるわけでもありません。

これは表現可能な組織構造です。実際に製品で稼働しているかを示すには、その製品のバインディング、権限、実行の証拠が必要です。図の状況はダウンロード可能な構造フィクスチャとは異なります。フィクスチャの A、B 両チームは分析担当と品質確認担当の両方を再利用してインスタンスのバインディングを説明しており、実際の検知エンジニアリング役割は設定していません。

## 04 技術的に定義、インスタンス、一回の実行を区別する

Worker 定義は AI 従業員の役割説明と作業契約に相当し、Worker インスタンスは Teloa の特定の AI 従業員に対応します。Run はその従業員の一回の実行です。役割テンプレートを更新しても、旧 Run は元のバージョンを保持します。モデルを変更しても、従業員の履歴を別の主体の履歴へ移す必要はありません。

![Teloa を例にした Worker 定義、AI 従業員インスタンス、Run、成果検収](../diagrams/en/architecture.png)

*Teloa を例にした Worker 定義、AI 従業員インスタンス、Run、成果検収。*

**技術的な経路は、標準定義 → 契約検証 → ホストのバインディング → 一回の Run → 固定成果 → 検収記録 → 業務への採用です。** 各段階が異なる問いに答えます。

| 層 | オブジェクトまたは段階 | 記録・確認する内容 |
| --- | --- | --- |
| 標準定義 | コア定義と作業拡張 | `id`、`revision`、`kind`、メンバーの固定参照、責務、作業入出力、依存関係、協業、検収要件 |
| ホスト設定 | 契約と能力の検証 | 参照の存在、入出力契約の完全性、必須能力の対応状況。不足があれば影響する作業を未準備とする |
| ホスト設定 | Worker インスタンスとバインディング | 特定 AI 従業員の持続的なアイデンティティと、その作業の資料・モデル・アプリ接続・有効な権限 |
| 実際の実行 | Work、タスク、Run | Work は繰り返し呼び出せる作業契約、タスクは具体的な一回の依頼、Run は一回の実行の入力・定義バージョン・実際の実行主体を記録する |
| 作業の納品 | 固定成果 | 閲覧できる成果の内容、バージョン、証拠、実際の貢献者。「実行終了」という状態だけではない |
| 作業の納品 | 検収記録 | 誰がどの要件でどの成果バージョンを確認し、どう判断したか。独立性が必要なら実際の貢献者も確認する |
| 業務判断 | 採用記録 | 責任者が成果を使用するか。採用と検収は別記録であり、公開や封じ込めの権限を自動付与しない |

たとえば「資料要約役割のリビジョン 2」は定義であり、それから作成した「資料整理アシスタント」はインスタンスです。今週と来週の要約は二つのタスクで、それぞれ Run と成果を保持します。テンプレート更新は旧 Run を書き換えず、旧成果の帰属を新しい従業員に移しません。

コア形式は `agent` と `organization` だけを維持します。Worker は `agent` と必須作業拡張、Team は `organization` と協業契約、Org はさらにガバナンス契約を用います。同じ参照とバージョンのルールで構成でき、製品ごとの呼称に別のファイル型を作る必要はありません。

ホストは Teloa のように、定義を実際に動作させるプラットフォームです。定義を実際のインスタンス、資料、ツール接続、モデル、認可主体にバインドし、入力と依存関係を確認し、実行と成果を記録します。ファイルのインポートは解釈待ちの定義を取得するだけで、アカウント接続、権限付与、実行開始、定例作業の有効化を自動的に行いません。構造検証、設定の準備完了、実行成功、成果検収、業務への採用はそれぞれ別の証拠を必要とし、互いの代用にはなりません。

## 05 フィールドごとに確認できる例

[資料要約 Worker](../examples/document-worker.json)は、すべての必須フィールドを持つ完全な JSON 定義です。`summarize` は空でない `material` 文字列を受け、空でない `summary` と文字列配列 `openQuestions` を出力します。以下は手書きの学習用の入出力例です。

```json
{
  "material": "示例周报：甲项目本周完成三份资料摘要。第二份缺少来源日期，负责人要求补充。材料没有提供工时或客户反馈。"
}
```

```json
{
  "summary": "甲项目本周完成三份资料摘要，其中第二份仍需补充来源日期。",
  "openQuestions": [
    "第二份资料的来源日期是什么？",
    "现有材料未提供工时或客户反馈，无法据此评价效率或满意度。"
  ]
}
```

入力は「プロジェクト A は今週三件の資料要約を完了した。二件目は出典日付が不足しており、責任者が補足を求めた。工数や顧客の意見は資料にない」という週報です。出力の要約はこの事実だけをまとめ、未解決の問いとして二件目の出典日付と、工数・顧客意見がないため効率や満足度を評価できない点を列挙しています。

構造検査はフィールド不足や型の誤りを検出できます。責任者はさらに、内容が資料に忠実か、工数データがないのに「効率が向上した」と書いていないかを確認します。検収は固定された出力バージョンに対して行い、変更後は合意した検査を再度実施する必要があります。

SOC の分析でも同じ関係を再利用できます。学習資料が WAF の HTTP 403 レコード一件だけなら、報告書はそのレコードが裏付ける結論を説明し、バックエンドやエンドポイントの証拠が不足していることを明記します。それだけでサーバー侵害や完全な安全を断定できません。深い調査に必要なデータは明確な不足事項として示し、遮断や隔離には対応するツールと権限が必要です。この例は実環境へ接続せず、攻撃も実行していません。

## 06 Grok Bot と Teloa の対応

Teloa の AI 従業員は AI Worker の製品上の表現であり、Grok Bot も AI Worker として説明できます。AI 従業員と Bot はそれぞれの製品概念を保ち、AI Worker が共通の技術定義を提供します。対応付けでは責務、作業契約、ホスト動作を個別に確認します。Grok の公開設計は持続する Bot と Skills、Routines などの構成を紹介しています。これは概念上の比較を可能にしますが、変換器の存在や公式な互換認証を意味しません。[Grok の設計説明](https://x.ai/news/designing-grok-bot)

| 製品概念 | 本仕様での対応 | 対応付け時の確認 |
| --- | --- | --- |
| Teloa の AI 従業員、Grok Bot | Worker 定義と実際のインスタンス | 持続的なアイデンティティ、責務、作業 I/O、検収の完全性 |
| 役割プロンプト、Bot profile | `instructions` と `responsibility` | 作業の境界が具体的か。不足契約を名前から推測しない |
| Skills、知識、SOP | 用途別に参照する `resources` | 実際のバージョン、出典、作業依存関係 |
| ツールまたはプラグイン | 能力参照、アプリケーションリソース、ホスト接続 | 実際の権限。資格情報はホストに残す |
| Teloa のグループとプロジェクト | チームの会話とコンテキストを入れる場 | 分担、引き継ぎ、チーム成果契約の明示が引き続き必要 |
| Grok Team Bot | 共有 Worker | 利用者の権限、私的会話、個人の定例作業を分離して保持 |

Grok Team Bot の文書は、複数人が同じ一つの Bot を使う形を説明します。複数の Worker が分担して一つの成果を作る AI Team とは異なります。共有 Worker を対応付ける場合、個人の定例作業はホストの私的設定に残し、共有定義には含めません。作成者が明示的に公開し、私的内容を除いたテンプレートだけを共有でき、インポート後も自動的には有効化しません。[Team Bots](https://docs.x.ai/grok-bot/team-bots)

Teloa の詳しいフィールド対応と未対応項目は[マッピング文書](mappings.md)を参照してください。

## 07 既存仕様を再利用し、範囲を明確に保つ

OASF は Agent の発見レコード、分野、能力分類を提供し、候補能力を探すのに役立ちます。本仕様はネイティブな分類とバージョンを保持し、作業契約で入力、出力、検収を別途定めます。OASF の分類上のスキルと、実行可能な Skill パッケージは同じ種類のオブジェクトではありません。[OASF Record Guide](https://docs.agntcy.org/oasf/agent-record-guide/)

Oracle Agent Spec のコンポーネント参照、入出力、構成定義は再利用できる設計です。本仕様はこれらを参考にしていますが、特定バージョンのマッピングではインターフェース、参照、実行の意味をそれぞれ変換する必要があります。フィールド名を変えただけで相互運用できるとはいえません。[Oracle Agent Spec 26.1.2](https://oracle.github.io/agent-spec/26.1.2/agentspec/language_spec_26_1_2.html)

JSON は固定定義の交換に使い、YAML は作成に使用できます。YAML の変換では、重複キー、アンカー、エイリアス、明示的タグ、非有限数、複数文書など規約外の入力を拒否し、数値と文字列の意味を保たなければなりません。たとえば `revision: "1"` は文字列であり、`revision: 1` は型エラーで拒否されます。同一リビジョンの二つのファイルを、独立して自由に変更できる作成元にしてはなりません。

## 08 導入を始めるには

既存の仕事を一つ選び、入力、出力、依存関係、責任位置、検収を明確にします。実際のインスタンスで実行した後、受信側が実際に取得した資料と固定成果を確認してからチームへ拡大します。現在のプラットフォームが重要な制約を満たせない場合、対応する作業を未準備と表示します。

本版はまずこれらの関係を明確に定義することを目指します。業界で共同採用できる仕様となるには、独立実装の相互運用の証拠、非 SOC シナリオ、公開の変更議論が必要です。リポジトリは Apache-2.0 ライセンスを採用しています。具体的な曖昧さや反例からの参加を歓迎します。[標準リポジトリ](https://github.com/teloa-ai/ai-worker-standard) · [フィードバック](https://github.com/teloa-ai/ai-worker-standard/issues)
